# 安全响应流程（内部）

面向值班人 / 负责人的**可执行**流程：发现 → 分级 → 止血 → 修复 → 验证 → 披露与复盘。
对外口径见仓库根目录 [`SECURITY.md`](../SECURITY.md)。

原则只有三条：

1. **先止血，再根治**——P0 优先让"坏事停止扩大"，不追求当次就写出完美补丁。
2. **每一步都要有证据**——证据是可复跑的命令与其输出，不是"我看过了"。
3. **不留后门式修复**——禁用功能必须写清恢复条件与到期时间，不许永久静默关闭。

---

## 1. 发现（Detection）

### 1.1 来源

| 来源 | 入口 | 值班人动作 |
| --- | --- | --- |
| 外部报告 | `security@example.com`（**⚠️ 占位，待老板替换**） | 当天确认收到，按第 2 节初判 |
| CodeQL 告警 | GitHub → Security → Code scanning（`.github/workflows/security.yml` 的 `codeql` job 上传） | 去重后按影响面分级 |
| 依赖漏洞 | `dependency-audit` job（**观测态**，见 `.github/workflows/security.yml` 注释） | 命中 high/critical 时人工复核可达性 |
| 密钥泄漏 | `secret-scan` job 变红；本地 `pytest tests/test_secret_scan.py` | 视为 P1 起步（见第 2 节） |
| 日志 / 监控 / 客户反馈 | 日志中的 500、403 突增、异常 UA、越权投诉 | 先固化证据再动手改动 |

### 1.2 第一条动作：固化现场（10 分钟内）

```bash
# 1) 先备份，再动任何东西。备份只读真实库，不改不删。
./tools/backup.sh                       # 产出 aieos-backup-YYYYmmdd-HHMMSS/ + .tar.gz
                                        # 内含 aieos.db 一致性快照、api.env、jwt_secret.key、manifest.json

# 2) 记录现场（别在终端里打印密钥内容，只记文件名/行号/时间）
git -C . rev-parse HEAD                  # 出事版本
git -C . log -1 --format='%ci %s'        # 出事先最后一次提交
```

`tools/backup.sh` 产出的 `manifest.json` 里有每个文件的 sha256，**这就是事后取证的
证据锚点**：复盘时要能证明"分析过的库/配置"与"出事时的库/配置"是同一份。备份目录与
文件权限为 0700/0600，且脚本不会把 `.env`、JWT 密钥内容打到 stdout/stderr——报告或
工单里引用备份时，只写路径与 sha256，不要贴内容。

## 2. 分级（Triage）

24 小时内（P0 为 2 小时内）必须给出初判，并在工单里写下**判断依据**（哪条数据、哪个
端点、哪个租户边界被突破）。分级不用"感觉严重"，只用下面这张表：

| 级别 | 判定（满足任一即升级） | 典型例子 | 响应 / 修复（SLA） |
| --- | --- | --- | --- |
| **P0** | 数据泄露；跨租户**越权写**；远程代码执行；认证绕过 | 未鉴权就能读任意租户的文件；bob 能 PATCH alice 的 agent；SSRF 打到元数据服务；提示词注入可执行本机命令 | 24h 响应 / **72h 修复或上线缓解** |
| **P1** | 跨租户**越权读**；密钥泄露风险；可绕过租户边界但需登录 | 只读 IDOR、事件日志跨租户可见、`jwt_secret.key` 疑似外发、模型 Key 出现在日志、弱默认口令 | 3 工作日响应 / **7 天修复** |
| **P2** | 其余：需高权限才能触发的信息泄露、依赖 medium、加固类 | 管理端回显内部路径；CSP 缺失；依赖 CVE 但不可达 | 5 工作日响应 / **下个版本** |

升降级规则：

- 初判 P1，但已确认**有多租户数据被读过**且无法排除被下载 → 升 P0；
- P0 在 72h 内无法根治时，必须上线缓解（回滚 / 关功能 / 轮换密钥）并书面写明
  "根治未完成 + 到期时间 + 负责人"，不允许静默降级；
- 只影响开发环境、且生产默认不可达的，可降级并记录理由。

## 3. 止血（Containment）

按"影响面最小、可逆、可验证"排序。以下动作都是**运维动作**，不改业务代码：

| 场景 | 止血动作 | 恢复条件 |
| --- | --- | --- |
| 越权 / 鉴权缺陷可被利用 | 回滚到上一个正常 tag；或在下游反代/WAF 先封路径（`/api/...`） | 修复版本上线且验证通过 |
| 某个功能被用作攻击面（如出站请求、文件下载、插件执行） | 关闭对应开关 / 下线该路由入口；在 `CHANGELOG` 记一条"临时下线" | 修复 + 针对该功能的回归用例并进 |
| 密钥疑似泄露 | **立即轮换**（附录 A），并按时间窗重签所有会话 | 新密钥上线 + 旧密钥确认失效 |
| 数据库被越权写 | 用 `tools/backup.sh` 的快照做定点回补；禁止整库覆盖式恢复 | 数据核对通过 + 审计结论落地 |
| 依赖 0day | 临时 pin 到安全版本或用 `ignore` 之外的覆盖方式；不要改业务逻辑绕 | 上游修复发布 |

止血阶段的硬约束：

- **先备份再动手**（`./tools/backup.sh`），回滚前也备份——否则回滚会毁掉取证素材；
- 每个动作记录"谁 / 何时 / 执行了什么命令 / 影响哪个租户 / 如何撤销"；
- 关闭功能必须写**到期时间**，到期未恢复要在周会上升级。

## 4. 修复（Fix）

1. 从 `main` 切修复分支，**不要在同一分支混入重构**（评审时无法区分行为变化）。
2. 修复必须带**能复现原问题的失败用例**（先红后绿）：越权类放进
   `apps/api/tests/test_tenant_matrix.py` 的参数化矩阵（资源族清单见
   `apps/api/tests/tenant_matrix_registry.py`），或新增专门的 `test_*.py`。
3. 若某越权点暂不能修，只能加 `known_leak` 标记 + allowlist 条目，**必须同时**：
   - 写明触发条件与影响面；
   - 在 `docs/10_KNOWN_ISSUES.md` 登记；
   - 给出修复时间点（这类条目不允许长期存在）。
4. 涉及密钥/出站请求的修复，顺带检查：日志是否打印凭据、错误响应是否回显上游报文、
   重定向是否跟随到内网（SSRF）。
5. PR 描述里**不写利用步骤**，只写"修了什么、如何验证"。合并后再补充说明。

## 5. 验证（Verification）

### 5.1 必跑（缺一不可）

```bash
# 后端全量测试（离线、SQLite、不连真实库）
cd apps/api && .venv/bin/python -m pytest -q

# 租户权限矩阵：属主正向对照 + 外部租户拒绝 + 写端点未改动，三件事同时验证
cd apps/api && .venv/bin/python -m pytest tests/test_tenant_matrix.py -q

# 密钥扫描：确保修复过程没把新凭据带进被跟踪文件
cd apps/api && .venv/bin/python -m pytest tests/test_secret_scan.py -q

# 交付前总门禁：pyflakes / 导入 / mapper / 契约 / 前端 tsc+eslint / 测试 / 端到端试跑
./tools/check.sh
```

为什么必须同时跑 `test_tenant_matrix.py`：它每个用例都先做**属主正向对照**
（alice 调同一端点必须成功），再做外部租户拒绝（bob 必须 404/403），最后校验
bob 的写尝试没有改动 alice 的数据。只看"bob 被拒绝"会假绿——端点被改坏时 bob
同样"被拒绝"。修复越权时，这条正向对照就是"没把功能改死"的证据。

### 5.2 建议补跑

- 方言护栏：`AIEOS_TEST_DATABASE_URL=postgresql+asyncpg://... pytest -q -o asyncio_default_test_loop_scope=session`
  （SQLite 会吃掉方言差异，PG 才是生产形态）；
- 端到端：`python3 tools/e2e_smoke.py`（假模型 + 临时库，不需要密钥）；
- 前端：`cd apps/web && npx tsc --noEmit && npm run test`。

### 5.3 证据链（复盘时按此顺序贴）

| 环节 | 证据 |
| --- | --- |
| 现场快照 | `tools/backup.sh` 输出目录 + `manifest.json`（含 sha256） |
| 漏洞存在 | 修复前的失败用例输出（红） |
| 修复有效 | 修复后的同一用例输出（绿）+ `test_tenant_matrix.py` 全绿 |
| 没有夹带凭据 | `test_secret_scan.py` 全绿（扫 `git ls-files`，只扫被跟踪文件） |
| 功能没被改坏 | `tools/check.sh` 全绿（含契约门禁与端到端主链路） |
| 自动化兜底 | `.github/workflows/security.yml` 的 `codeql` / `secret-scan` 绿；`dependency-audit` 观测日志 |

## 6. 披露与复盘（Disclosure & Postmortem）

### 6.1 披露

- 修复版本发布后 **7 天**对外披露（与报告者协商，报告者要求更晚则从其意愿）；
- 披露内容：受影响版本、影响面、修复版本、用户需做的动作（升级 / 轮换密钥）、
  致谢（经同意）。**不含**可直接复用的利用代码；
- 同步更新 `CHANGELOG.md` 的 `Security` 段落与 `SECURITY.md`（若分级或范围有变化）。

### 6.2 复盘模板（P0/P1 必填，发布后 5 个工作日内）

```markdown
# 安全事件复盘：<一句话标题>

- 事件编号 / 级别：SEC-YYYYMMDD-01 / P0
- 发现时间 / 初判时间 / 止血时间 / 修复上线时间：
- 发现来源：外部报告 / CodeQL / 依赖审计 / 密钥扫描 / 监控
- 受影响版本与租户：
- 现场快照：<tools/backup.sh 输出目录>（manifest sha256: ...）

## 1. 时间线（UTC+8）
| 时间 | 动作 | 执行人 | 证据 |
| --- | --- | --- | --- |

## 2. 根因
（直接原因 → 为什么测试没拦住 → 为什么评审没发现。写到"机制"层，不写"某人疏忽"。）

## 3. 影响面
（数据：哪些表/文件/租户；时间窗；是否可被批量利用；是否需要通知客户。）

## 4. 止血与修复
（回滚/关功能/轮换密钥的具体动作；修复改了哪几个文件；为什么这样改。）

## 5. 验证
（贴 test_tenant_matrix.py、test_secret_scan.py、tools/check.sh 的结论行。）

## 6. 改进项（每条必须有负责人 + 截止日期 + 验证方式）
| 改进 | 负责人 | 截止 | 如何验证已生效 |
| --- | --- | --- | --- |

## 7. 未解决 / 接受的风险
（写清为什么接受、到期复核时间。）
```

改进项验收标准：**能自动化的一律落成测试或流水线门禁**，不接受"下次注意"。
例如新增攻击面 → 进 `tenant_matrix_registry.py`；新凭据 → 进 `test_secret_scan.py`
的类型规则；新依赖风险 → 调整 `.github/dependabot.yml` / `security.yml`。

## 附录 A：密钥轮换操作清单

> 通用前置：先 `./tools/backup.sh`（会备份 `.env` 与 `jwt_secret.key`，权限 0600，
> 不打印内容）；轮换期间**不要**把新旧密钥写进任何工单、聊天或提交信息。

### A.1 `JWT_SECRET`（会话签名）

当前实现：`apps/api/app/core/config.py` 在启动时解析 `JWT_SECRET`；若为空/弱值，
会**自动生成并落盘**到 `jwt_secret.key`（路径可用 `AIEOS_JWT_SECRET_FILE` 指定）。
密钥只有一把、没有 kid/双密钥并行，**轮换 = 全量用户重新登录**。

1. 通知：轮换窗口（建议低峰），说明"所有登录态将失效"；
2. 生成新值（两者等价，取其一）：
   ```bash
   python3 -c "import secrets; print(secrets.token_urlsafe(48))"
   openssl rand -base64 48
   ```
3. 写入两处并保持一致：
   - `apps/api/.env` 的 `JWT_SECRET=<新值>`；
   - 密钥文件（若启用）：`AIEOS_JWT_SECRET_FILE` 指向的文件内容替换为新值，权限 `chmod 600`；
   - Docker / 一键部署：更新 compose 的 env 或宿主机 env 文件，**重新创建容器**（不是 restart 旧容器）；
4. 重启服务 → 用新账号登录验证签发正常 → 用旧 token 请求必须 401；
5. 确认旧 `.env` / 旧密钥文件副本（备份目录内的）已按保留策略隔离，不得留在共享盘；
6. 记录：轮换时间、执行人、验证结论（401 证据）。

### A.2 模型 Key（上游大模型凭据）

当前实现：模型行上存的是**环境变量名**（`model_row.api_key_env`），网关按名从
`.env` 取值（`apps/api/app/model_gateway.py` 的 `_resolve_api_key`）。因此轮换只需
**改 `.env` 里的值，不要改变量名**——改变量名会让模型配置指向空值。

1. 在上游控制台**先建新 Key、再删旧 Key**（避免空窗）；
2. 更新 `apps/api/.env`：`OPENAI_COMPAT_API_KEY` / `ANTHROPIC_API_KEY` / `GEMINI_API_KEY`
   等（清单见 `.env.example`），以及安装向导写入的其他 provider 变量；
3. 重启后端 → 用一个真实请求验证（或 `requires_llm` 用例），确认不再 401/403；
4. 检查日志与错误响应没有回显 Key（只应出现"未配置/鉴权失败"，不应出现 `sk-...`）；
5. 如果 Key 曾进入 git 历史：仅轮换不够，需按第 4 节修复 + 评估历史重写（重写需负责人批准）。

### A.3 License 公钥（离线授权校验，若已启用）

**现状说明**：当前仓库内**未找到** License 公钥校验实现（检索 `LICENSE_PUBLIC_KEY`、
`license_public_key`、`verify_license` 均无命中）；`packaging/keystore/ai-eos.p12` 是
**macOS 代码签名证书**，不是授权公钥（口令与打包流程见 `packaging/打包说明.md`）。
因此本小节为**预案**，一旦接入离线授权校验，按下列清单执行：

1. 新密钥对在离线机器生成，**私钥永不入库、不进 CI**；只把公钥随客户端产物内嵌；
2. 客户端发新版本时带新公钥；旧版本在一段过渡期内同时接受旧公钥签发的 License；
3. 过渡期截止时间写进 `CHANGELOG.md`，到期后旧公钥从产物中移除；
4. 若怀疑私钥泄露：立即停止签发、作废旧公钥、强制客户升级，并按 P0/P1 分级处置；
5. 公钥/私钥的存放位置、备份与访问人清单在内部台账登记，不写在公开文档里。

## 附录 B：不要做（Don't）

1. **不要在公开 issue / PR / 群聊贴密钥、`.env`、数据库导出、真实客户数据**；
   证据只贴"文件:行号 + 前 3 位"，数据用自造假租户。
2. 不要在生产直接改库"修数据"——先 `tools/backup.sh`，改动前记录 SQL 与影响行数。
3. 不要在未备份时回滚或覆盖数据库；回滚前也要备份（否则毁掉取证素材）。
4. 不要用"删测试 / 放宽断言 / 加 xfail"来让流水线变绿；暂不能修只能标
   `known_leak` 并登记 `docs/10_KNOWN_ISSUES.md`，且给修复期限。
5. 不要在修复 PR 标题/描述里写利用步骤；合并后再补充。
6. 不要为了复现把真实模型 Key 放进代码、夹具或提交信息——`test_secret_scan.py`
   会扫 `git ls-files`，命中即红。
7. 不要让安全相关 PR 自动合并（含 Dependabot `deps-major`）；也不要改
   `.github/workflows/ci.yml` 的门禁阈值来换绿色。
8. 不要在没有到期时间的情况下永久关闭某项功能；下线必须写恢复条件。
9. 不要跳过 `test_tenant_matrix.py` 直接合并越权修复——没有正向对照的"通过"是假绿。
