# AI-EOS 万能基座升级方案（V6：「乐高基座」）

- 日期：2026-11-16
- 基线版本：v5.16.1（pytest 1207 项 0 失败）
- 方法：仓库逐模块代码盘点（带 文件:行号）+ 业界开源对标调研（Dify / Coze / n8n / RAGFlow / Composio / MCP / A2A / Odoo / ERPNext / 金蝶 / 用友，2026-11 时点）
- 目标：把 AI-EOS 从「单公司数字员工操作系统」升级为**可插拔的万能基座**——插件即积木、行业包即套装、企业定制即私有图纸、外部系统即数据源、Agent 即干活的工人。

---

## 0. 一页结论

**不需要推倒重来。** 代码盘点显示：AI-EOS 已经拥有一个相当完整的「数字公司内核」——118 张表、90+ 路由模块、带审批节点的工作流引擎、MCP 双向通道、模型 provider 插件加载、Fernet 凭据保险库、任务断点与人工介入。真正缺的不是内核，而是**把写死的能力改造为可插拔的协议**，并补上三条缺失的横向设施。

一句话战略：**内核不动，长出四层 + 两条横切 + 一个组织模型。**

```
┌─────────────────────────────────────────────────────────────┐
│  L4 企业定制层    每企业的开关/扩展字段/私有流程/白标/部署形态    │
├─────────────────────────────────────────────────────────────┤
│  L3 行业包        行业实体模型 + 行业工作流 + 行业指标 + 知识包  │
├─────────────────────────────────────────────────────────────┤
│  L2 插件系统      manifest + 市场 + 三类运行形态 + 权限沙箱     │
├─────────────────────────────────────────────────────────────┤
│  L1 能力总线      统一工具注册表（MCP-native，一切工具皆协议）   │
├─────────────────────────────────────────────────────────────┤
│  L0 内核（已有，强化）  任务/运行时/模型网关/工作流/调度/组织     │
└─────────────────────────────────────────────────────────────┘
   横切 A：数据平台   连接器框架 → 规整层 → 主题域 → 指标层 → AI 消费
   横切 B：安全体系   隔离 → 加密 → 字段级权限 → 出站闸门 → 审计
   横切 C：人机组织   自然人 ↔ 多 Agent；老板 ↔ Agent 军团；Agent ↔ Agent
```

与五个需求的对应：

| 你的需求 | 方案落点 |
|---|---|
| 1. 万能基座（类 Dify，乐高式组合） | L1 能力总线 + L2 插件系统 + 市场 |
| 2. 行业插件 | L3 行业包 ×10（首批清单见 §4.3） |
| 3. 企业定制 | L4 企业定制层 |
| 4. 对接 ERP/CRM 等管理软件 | 横切 A 连接器框架（首批 5 连接器） |
| 5. 数据安全 + AI 处理 + 多 Agent 组织 | 横切 A 数据规整/指标层 + 横切 B 安全 + 横切 C 组织模型 |

## 2. 五个核心差距（对照五条需求，逐条核实）

1. **工具面太窄（最大差距）**。native 大模型链路的函数工具只有 2 个：`tools.py:67` `TOOLS = [web_search, web_fetch]`。能力包提示词里宣传的 computer_* 工具集实际走 sidecar/Hermes/Codex 通道，与 native 链路是**两套互不相通的体系**——模型「看到的工具」和「真正能用的工具」不一致。升级方向：统一工具总线（§4.1）。
2. **插件 = 目录登记，不是能力插件**。`plugin_service.py` 的 CATALOG 是 5 条硬编码条目（1 条真 npm 包 + 4 条占位），没有 manifest 标准、权限声明、版本管理、分发市场、沙箱分级。它解决的是「桌面工具装没装」，不是「基座能不能长出新能力」。
3. **知识检索无向量**。`knowledge_engine.py:1-6` 自述「token-overlap scoring…vector-ready for future pgvector swap」；`semantic_search.py` 是 BM25 重排并明确写 TODO 接 embedding。中文语义检索（同义改写、跨词匹配）目前靠十组手工同义词硬撑。
4. **外部系统对接缺框架**。现状是文件 batch-import + MCP 入站直通（需人工逐个配置 endpoint）。缺：连接器抽象（凭据轮换、增量游标、限流重试、schema 映射、同步任务监控）。国内 ERP（金蝶/用友）与开源 ERP（Odoo/ERPNext）都有官方 API / MCP Server，但 AI-EOS 还没有吃它们的管道。
5. **行业与企业维度缺失**。`capability_packs.py:112` 的 DEPT_CAPABILITY_PACKS 是「部门 → 能力包」映射，不是「行业 → 业务对象/流程/指标」包；企业定制目前只有数据隔离，没有 per-company 扩展字段、私有流程模板、白标。

## 4. 目标架构

### 4.1 L1 能力总线（Tool Bus）——最先做，一切的地基

**原则：一切工具皆协议。** 无论工具来自内置函数、技能、能力包 sidecar、插件还是外部系统，统一注册、统一描述、统一授权、统一审计。

- **统一注册表**：新表 `tool_registry`（id/company_scope/来源类型/name/description/参数 JSON Schema/风险级/所需权限/实现引用）+ `agent_tool_grants`（哪个 agent 被授予哪些工具）+ 工具调用审计并入 `event_log`。
- **双形态暴露**：每条工具同时产出 ① OpenAI function-calling schema（喂 native 链路）② MCP tool 描述（喂外部 Agent / 出站 MCP Server）。native 链路与 sidecar 链路的「两套工具体系」就此合并——修掉 §2-1 的一致性缺口。
- **执行路由**：`tools.py` 的 `execute_tool` 扩展为总线 dispatcher：内置函数直调 / skill 走 `skill_system` / sidecar 走 `computer_agent` 通道 / MCP 远程走 `McpHttpAgentAdapter`。SSRF 闸门、审计、结果截断（`MAX_TOOL_RESULT_CHARS`）全在总线一层收口，不再散落。
- **出站 MCP Server 扩容**：`mcp.py` 现有 7 个 aieos.* 工具改为从总线动态生成——AI-EOS 的每个员工能力自动成为外部 Agent 可调用的工具。

### 4.2 L2 插件系统

**Manifest v1**（YAML，随插件分发）：

```yaml
id: kingdee-k3c-connector
name: 金蝶云星空连接器
version: 1.2.0
category: connector        # model_provider | tool | skill_pack | connector | workflow_template | industry_pack
runtime: mcp_stdio          # inprocess_python | sidecar_process | mcp_stdio | mcp_http
permissions:
  - network.kingdee.com     # 网络域白名单（复用 SSRF 闸门的思路）
  - secret.read:kingdee     # 凭据命名空间
  - data.write:customers    # 数据域
risk: high
config_schema: { ... }      # 安装时向用户收集的配置（密钥、站点 URL）
```

- **三类运行形态**（复用已有通道，不发明新机制）：
  1. `inprocess_python`——现有 `BaseSkill` + `load_plugin_skills()` 路线，适合轻计算；
  2. `sidecar_process`——现有 computer/browser/hermes/codex 路线，适合操作本机；
  3. `mcp_stdio / mcp_http`——**新主路线**：第三方生态（Odoo/ERPNext/Composio/自研）直接以 MCP Server 接入，进程隔离天然成立。
- **市场**：`plugin_service.py` 的硬编码 CATALOG 升级为「manifest 注册表服务」：分类浏览、权限明示、一键安装向导（MCP 形态 = 填 endpoint/凭据；npm 形态 = 现有托管安装）、版本与更新、企业私有插件源（本地目录 / git URL / 自建 registry）。
- **沙箱分级**：risk=low（纯计算）可 in-process；risk=medium（网络/文件受限域）走 MCP 子进程 + 白名单；risk=high（shell/凭据/全库）必须逐次审批 + 预算扣减（复用 budgets）。

### 4.3 L3 行业包（Industry Packs）

**定义**：行业包不是代码，是一份「精选积木 + 行业图纸」的安装清单 = `行业实体扩展（custom fields）+ 行业工作流模板 + 行业技能/工具集 + 行业知识包 + 指标看板 + 术语表`。安装行业包 = 一个事务里种好全部配置（复用 demo.py 的「一键开箱」模式）。

| 私有连接器/插件 | 企业私有插件源（§4.2），不进公共市场 | plugin_service 扩展 |
| 白标 | logo/主题色/登录域名/术语替换（「公司」→「事务所」） | 新表 `company_branding` |
| 部署形态 | 单机 portable（已有）→ 团队服务器（Docker Compose）→ 专有云 | 保留三档 |
| 权限定制 | 角色即能力包组合：企业自建角色（VIEW/OPERATE/MANAGE 矩阵 + 数据范围） | 现有 Capability 体系扩展 |

### 4.5 横切 A：数据平台（对接 ERP/CRM + AI 规整）

**连接器框架（Connector SDK）**——新增模块 `app/connectors/`：

```
BaseConnector（抽象）        # discover_schema / pull_incremental / push / health_check
 ├ RestApiConnector         # 金蝶云星空 OpenAPI、用友 OpenAPI、销售易/纷享销客等
 ├ DatabaseConnector        # 只读连客户库（SQL Server/MySQL/PG），SQL 白名单 + 只读账号
 ├ McpBridgeConnector       # 直连 Odoo 20 官方 MCP / ERPNext 社区 MCP / Composio——成本≈0
 ├ WebhookReceiver          # 企微/钉钉/飞书回调推入
 ├ FileConnector            # Excel/CSV 定期导入（升级现有 batch-import）
 └ RpaConnector             # 无 API 的老系统，走现有 computer_use 能力兜底
```

- 凭据：`company_secret` + `secret_vault`（已有 Fernet 库）+ 新增 OAuth 托管流（授权回调、token 刷新、失效告警）。
- 调度：增量拉取（游标/水印字段）挂 `scheduler_engine` + `job_queue`，失败退避与断点续传；同步任务有监控页（成功率/延迟/行数）。
- **规整层（关键设计）**：各来源数据先落地，再映射到**统一实体模型**（Canonical Model）：客户 Contact / 企业 Account / 订单 Order / 产品 Product / 凭证 Voucher / 员工 Employee / 工单 WorkOrder…字段映射器 + 冲突规则（来源优先级 + 时间戳）。**这一层是「AI 能不能真干活」的分水岭**——没有它，每个 Agent 都要面对 N 套字段名。
- 主题域与指标层：销售域/财务域/生产域/人力域；`metric_registry` 表存指标口径（SQL/维度/粒度/权限），AI 通过**指标工具**取数（总线注册为 `metrics.query`），**不让模型裸写 SQL 打业务库**。
- AI 消费：RAG 管「知识」（制度/文档/话术），指标层管「数字」，报告引擎（doc_generator/report_templates 已有）管「交付件」，工作流管「例行动作」。用户点名的场景落到行业包工作流：拓客（线索挖掘→触达）、锁客（跟进/续费预警）、质量控制（质检单聚合→整改）、生产（排产/报工）、HR（排班/招聘漏斗/离职预警）。

### 4.6 横切 B：安全体系（分级演进，第一步已有底子）

| 级别 | 措施 | 现状 → 动作 |
|------|------|------------|
| S1 租户隔离 | company_id 全链路 + 行级 scope + Capability | **已有**（11-11 收口），保持 |
| S2 凭据安全 | Fernet 保险库、明文不落日志 | **已有**；补 OAuth token 刷新与泄露告警 |
| S3 静态加密 | 数据文件加密（SQLCipher 或字段级加密扩展 secret_vault） | 新做：先字段级（身份证/手机号/银行账号），全库加密随部署形态做 |
| S4 字段级权限 | 角色可见字段矩阵（销售看全客户手机号，客服只见脱敏号） | 新做：接在 Custom Fields Registry 与指标层 |
| S5 出站闸门 | 数据出系统（发邮件/webhook/工具传参）先过 DLP 规则：PII/财务批量外发需审批 | 新做：复用 SSRF 闸门的「逐跳复检」思路到数据面 |
| S6 审计与合规 | event_log 已全程留痕 → 补审计导出、留存策略、敏感操作双人确认 | 扩展 |

### 4.7 横切 C：人机组织模型（自然人 ↔ Agent 军团）

- **自然人 ↔ 多 Agent（1:N）**：新表 `member_agent_bindings`（user_id ↔ agent_id，关系：助理/下属/顾问）。每个自然人有一个「随身助理」（跨公司、个人记忆），加若干公司内下属员工。前端「我的员工」页 = 现有组织页过滤绑定关系。
- **老板 ↔ 军团**：owner 已有完整闭环——建司 → 组织生成 → CEO 拆任务 → 并行执行 → 简报/复盘/介入。补齐：Agent 军团的**预算总额**（budgets 已有单 Agent 粒度）、**审批汇聚**（workflow APPROVAL 节点 + 介入信箱统一成「待我审批」收件箱）、**接管模式**（一键接管某 Agent 的会话，已有 intervention MESSAGE 基础）。
- **Agent ↔ Agent**：任务委派链已有（parent_task）；跨公司/跨组织协作预留 A2A 接口（M5 后），出站 MCP Server（§4.1）就是雏形——外部 Agent 已经能调 aieos.create_task 派活给员工。
- **每个 Agent 的完整配置面**：模型（主/备/回退已有）× 工具集（总线授权，新）× 知识（两级 KB 已有）× 记忆（memory_engine 已有）× 能力包（已有）× 预算（已有）× 审批人（新）× 数据范围（行级+字段级，扩展）——这 8 个维度就是「每个人拥有很多 Agent，每个 Agent 都不一样」的落地。

## 7. 风险与未覆盖区（如实标注）

1. **SQLite 体量上限**：连接器数据量上来后（百万行级订单），需迁 PostgreSQL。alembic 已就绪、`background_jobs` 注释显示 asyncpg 引擎曾支持，但**迁移未实测**——M3 开始前要做一次 PG 真库回归。
2. **向量库选型**未最终拍板（本方案推荐 sqlite-vec 起步），M1 首周决策。
3. **插件沙箱强度**：in-process Python 插件不能算强隔离（同进程共享解释器），第三方插件一律默认推 MCP 子进程形态；in-process 保留给平台自研。
4. **行业包内容深度**依赖真实行业知识（费率、单据流、指标口径），本方案给出框架与首批模板骨架，落地每个包需要行业顾问输入校准——这是产品化成本，不是纯代码成本。
5. **金蝶/用友对接细节**：开放平台均有 API 配额与收费（用友 U8 开放平台明确按接口收费），商务条款未核实；标称接口覆盖面以官方文档为准。
6. **本方案的调研边界**：代码为静态逐模块核验 + 少量精读（tools/plugin_service/mcp/capability_packs/knowledge/secret_vault 等全文精读，其余为结构清点），未做连接器/插件的真机联调（目标模块尚不存在）；业界调研基于公开资料（2026-11 时点），未逐一注册试用。
7. **工作区现状**：`demo.py` / `demo.ts` / `test_demo_seed.py` 尚未提交入库（git status 未跟踪），M1 动工前先收口。
