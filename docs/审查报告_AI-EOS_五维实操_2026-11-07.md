### 3.2 【P0】设备 sidecar 护栏可被换行 / 单 `&` 绕过 —— 已实测执行

**这是本次审查最严重的问题，我不是读代码猜的，是跑出来的。**

`apps/device_agent/aieos_sidecar.py:168-178` 的分段函数只认 4 个分隔符：

```python
def _segments(tokens: list[str]) -> list[list[str]]:
    out: list[list[str]] = [[]]
    for tok in tokens:
        if tok in ("&&", "||", ";", "|"):   # ← 没有 "\n"，没有单个 "&"
            if out[-1]: out.append([])
        else: out[-1].append(tok)
    return [seg for seg in out if seg]
```

而 `:392` 是 `subprocess.run(command, shell=True, ...)` —— **shell 会把换行和单 `&` 当命令分隔符**，护栏却只检查了第一段。

实测结果（调用真实 `check_command`，返回 None = 放行）：

| 命令 | 护栏判定 | 应该 |
|---|---|---|
| `rm -rf /` | 拦截 ✅ | 拦截 |
| `ls && rm -rf x` | 拦截 ✅ | 拦截 |
| `ls\nrm -rf important_dir` | **放行 ❌** | 拦截 |
| `cat notes.txt\npython3 -c "print(1)"` | **放行 ❌** | 拦截 |
| `ls & rm -rf x` | **放行 ❌** | 拦截 |
| `pwd\nid` | **放行 ❌** | 拦截 |

并且我起了真实 sidecar 进程，用无害命令 `pwd\necho SECOND_COMMAND_RAN` 验证：**第二条命令真的执行了**，输出里出现了 `SECOND_COMMAND_RAN`。

**后端也挡不住，而且三层都漏：** `services/computer_service.py:454` 原样转发参数；`services/computer_policy.py:70` 的 `_SHELL_METACHARS = re.compile(r"[;&|`$<>]")` **不含 `\n\r`**，所以多行命令在 `:307` 不会被判定为「含 shell 元字符、需额外 scrutiny」；`_hard_block`（`:257`）只拦固定碎片（`rm -rf /`、`rm -rf ~` 等），`rm -rf important_dir` 不在名单里；「完全控制」档（`:349`）直接返回 `allow`，**连审批单都不生成**。于是命令直达设备，设备的最后一道护栏（`check_command`）又只检查第一段 → 全部执行。

**影响范围要说准确：** 本机执行器 `apps/api/app/computer_real.py:270` 的 `_SHELL_METACHARS = set(";|&<>$`\\\n\r")` **包含 `\n\r`**，且用 exec 不用 shell，**不受影响**。中招的是**远程设备链路**（后端 → 设备 sidecar）。也就是说：老板给远程设备开了「默认审批」档，看到审批单上写着 `ls`（或批准了一条看起来无害的多行命令），以为设备护栏会兜底，实际上第二行起完全不设防；开「完全控制」档则连审批都没有。

**修法（三处都要）：** ① sidecar `_segments` 增加 `\n`、`\r`、单 `&` 分隔；② 更稳妥的是 `check_command` 入口直接拒绝含 `\n\r` 的命令（与本机执行器 `computer_real.py:270` 同口径）；③ 后端 `services/computer_policy.py:70` 的正则补 `\n\r`，让多行命令在审批阶段就被标记出来。

### 3.3 【P1】`model_gateway` 缺 `trust_env=False` —— 已复现

`apps/api/app/model_gateway.py:65-72`：

```python
client = httpx.AsyncClient(timeout=HTTP_TIMEOUT, limits=HTTP_LIMITS)  # ← 没有 trust_env=False
```

httpx 默认 `trust_env=True` 会读 `NO_PROXY`。当用户的 `NO_PROXY` 里含 `[::1]`（Clash、Docker Desktop、很多公司脚本都会写），httpx 0.28.1 把它当 URL authority 解析，抛 `InvalidURL: Invalid port: ':1]'`。

**我做了决定性复现：** 同一请求，`trust_env=True` → InvalidURL；`trust_env=False` → 200 OK；把 `NO_PROXY` 里的方括号去掉 + `trust_env=True` → 200 OK。

**为什么这个 bug 特别坏：**

1. **模型发现能用，对话不能用。** `model_discovery.py:391` 显式写了 `trust_env=False`，所以向导里「拉取模型列表」成功、「测试连通」失败 —— 用户看到的是「明明能列出模型，一测就报错」，完全无法理解。
2. **错误信息误导。** 报的是 `Invalid port`，用户会去查自己的 base_url 和 Key，而真正的原因是他机器的代理环境变量。
3. **全仓 12 处 httpx 客户端，6 处缺、6 处有** —— 缺的：`model_gateway.py:70`、`services/im_webhook.py:184`、`automation_engine.py:113`、`skill_provisioning.py:214/250`、`api/routes/mcp.py:275`。有的：`external_agents.py:185/204/246`、`browser_agent.py:117-118`、`command.py:231`、`model_discovery.py:391`。**这是口径不统一，不是偶然遗漏。**

你的真实 `:8000` 进程没有代理变量，所以**你现在没中招**；但任何装了 Clash / Docker Desktop 的用户装上就坏。修法：12 处统一 `trust_env=False`，并加一条护栏测试禁止裸 `AsyncClient(`。

### 4.2 【P1】验收闭环断链 —— 老板拿不到决策点

**这是产品维度最严重的问题，我实测 + 代码双重确认。**

操作过程：派了 3 个任务给 3 个 AI（客户成功经理 / 支持专员 / 续费顾问），全部执行完成，交付中心确实出现了 3 个文件夹、每个 1 个 `.md` 文件、117 B、可下载。

然后：

- 任务中心「待验收」tab → **0**，提示「现在没有待验收的交付物」
- 成果中心（`/artifacts`）→ **「暂无成果 · 点击右上角「＋ 新建成果」开始」**
- API 查 `/tasks/inbox` → 3 条 completed，**`artifact_id` 全是 `null`**

**根因：** 系统里有两种「产出」，但主线只产第一种：

| | Asset（素材资产） | Artifact（成果/交付单） |
|---|---|---|
| 谁创建 | 任务执行、聊天 `[GENERATE_DOC]` → `agent_chat.py:592` | **只有** `POST /artifacts`（手工，`artifacts.py:92`）和行业包模板（`org_presets.py:302`，DRAFT） |
| 能做什么 | 下载 | 提交 / 审核 / 通过 / 退回 / 评论 / 版本留痕 |
| 主线会不会产 | **会** | **不会** |

而 `inbox.py:96-104` 判定「待验收」的条件是：任务 COMPLETED **且**有 `Artifact.task_id` 关联 **且**状态在 ACCEPTANCE_STATUSES **且** `accepted_at is None`。

**结论：正常「老板派活 → AI 干活」流程下，待验收永远是 0，成果中心永远是空，验收/退回 UI 永远点不到。** 老板只能去交付中心下载文件自己看 —— 这就退化成「AI 帮我写了个文档」，而不是「AI 员工交活、我验收」。「一人公司」的核心管理动作缺了。

修法：任务执行产出文件时，同步创建 Artifact 并挂 `task_id`，状态置 IN_REVIEW。这是一处服务层改动，不是大工程，但产品价值最大。

### 4.3 【P1】「创建并分发」不启动

按钮文案是 **「🚀 创建并分发给 3 名成员」** —— 火箭 emoji + 「分发」，任何用户都会理解为「这就开始干了」。

实测：点完，3 个任务全部停在 `TODO`。任务列表页的操作只有 ⏸暂停 / ⏹停止 / 🗑删除 / 🗑批量删除，**没有 ▶启动，也没有批量启动**。▶启动 只存在于任务详情页 —— 也就是说老板要逐个点进 3 个详情页各按一次启动。

我是靠 API `POST /tasks/{id}/start` 才让它们跑起来的。普通用户不会知道要这样做，他会以为产品坏了。

修法（二选一）：① 分发即启动（符合文案直觉）；② 文案改成「创建并分配」+ 列表页补 ▶启动 和批量启动。**我倾向 ①**，因为「一人公司」的老板不想管调度。

### 4.4 【P2】进度恒 0%

3 个任务 `status=COMPLETED` 但 `progress=0.0`，UI 显示 0%。老板看到「已完成 0%」会困惑。要么完成时置 1.0，要么完成态不显示进度条。

3. **用真实模型跑一遍主线并留下基线记录**（KNOWN_ISSUES #8）。现在所有「能力」声明都缺一个真实模型的验收证据。

## 5. 维度三：重度使用用户（7 / 10）

### 5.1 真生产力（实测好用）

- **⌘K 命令面板是这个产品最好的交互。** 实测：44 个页面可直达；空输入时给「最近访问 + 员工 + 常用动作」共 20 项；输入拼音 `renwu` → 精确命中「任务」和「新建任务」2 条；有 ↑↓ 选择 / ↵ 打开 / Esc 关闭 提示；还能「清空最近访问记录（只清本机，不影响数据）」。对于 44 个页面、侧栏只露 11 项的产品，**这是唯一可行的导航方式，而它做得很好。**
- **六维用量统计是真的。** `/token-stats` 四个 tab 全部实测有数据：个人（Agent 排行）/ 部门 / 公司 / 项目 / 任务 Top 消耗 / 场景。我跑完 3 个任务后看到：总 1.4K tokens（输入 1.3K / 输出 148）、4 次调用、客户成功部 1.0K、3 个任务各 339。**这不是假图表，是真计量。**
- **预算上限的文案很懂老板：** 「一人公司成本护栏：用量到顶 → 自动暂停（任务停下等老板调额），**不是 10 倍加价惩罚**」。范围可选公司 / 部门（虚拟账户）/ 员工，周期可选每天重置 / 累计不重置。而且后端真的在网关里强制执行（`model_gateway.py:902`），不是摆设。
- **交付中心按 Agent / 项目 / 任务三种分组**，实测 3 个 Agent 文件夹各自列出文件数、大小、最近日期。
- **诊断页信息密度高且可操作：** 6 项检查（数据库 / 磁盘 / 局域网 / 升级通道 / 执行状态健康 / 本机时间），异常项直接给修复命令「跑 `tools/publish_client_updates.py`」。**而且它诚实标注时区**：「体检完成 2026-11-07 08:55:10 **UTC**」+ 单独一行「本机时间 2026-11-07 **16:55**」—— 这是全仓时区处理最正确的一个页面。

### 5.2 【P2】时间显示差 8 小时（多处）

实测对照：

| 页面 | 显示 | 本地真实时间 |
|---|---|---|
| 指挥中心 / 活动流 | `08:46:21`、`08:47:30` | 16:46 CST |
| Token 统计 → 用量流水 | `11-07 08:48` | 16:48 CST |
| 诊断页 | `08:55:10 UTC` + `本机 16:55` | ✅ 正确 |

根因：后端序列化 naive UTC（`datetime.utcnow().isoformat()`，无 Z 后缀），前端 `Date.parse` 当本地时间解析。

**注意：工作区已经改了 10 个 web 文件做这件事，但没提交**（`automation` / `companies` / `memory` / `performance` / `tasks` / `tasks/[id]` / `templates` / `workflow-builder` / `login` / `WorkspaceChat`）。**`token-stats` 和 `dashboard` 不在改动清单里，所以还在漏。** 建议：把这批改动提交，然后扫完剩余页面；更根本的是后端统一输出带 `Z` 的 ISO 串，前端就不需要每页各修一遍。

### 5.3 【P2】批量操作缺「启动」

任务列表有 🗑批量删除，**没有批量启动**。对「一次派 10 个活」的重度用户，这是每天要用 10 次的动作。详见 4.3。

### 5.4 【P2】状态与计数不一致

- 任务详情页：「任务日志 **0 条**」，但同页「事件流」显示 **2 条事件**。两个计数器口径不同，用户会以为日志丢了。
- 活动流 / 事件流显示**原始枚举**：`task.dispatched`、`STATUS_CHANGED`，而不是中文。重度用户每天看几十条，英文枚举是持续的认知摩擦。
- 用量统计「场景维度」每行末尾显示 `· 0%`。取证：`tokens.py:410` 的 `cost_pct` 是**费用占比**，没配单价时恒为 0。它紧跟在 tokens 和次数后面、没有任何标签，**看起来像一个坏掉的进度百分比**。建议无单价时不显示，或标注「费用占比」。

### 5.5 【P2】用量流水能看不能导出

实测 `/token-stats` → 用量流水 tab：只有「⟳ 刷新」，**没有导出按钮**。后端 `routes/licensing.py:97` 有 `/billing/invoices/export.csv`，但前端零调用方。重度用户（尤其是要拿给财务看的）只能手抄 100 行。

### 5.6 未走查的部分

作战室实时盯盘、会议中心、工作流编排、日程触发、插件安装、设备真机执行 —— 这些是重度用户的深水区，本次没走。**不能给它们打分。** 尤其设备 sidecar 有已实测的 P0 绕过（3.2），在修好之前不建议开远程设备链路。

## 6. 维度四：小白用户（7.5 / 10）

### 6.1 首次上手链路做得认真（实测）

从 `/login` 开始走完整条：

- **注册后自动跳 `/setup`**，不需要用户找入口。
- **密码校验是逐字段内联中文提示**，实测覆盖：空值、少于 8 位、两次不一致、必须含字母。还有强度指示条。**不是提交后才报一个红框。**
- **诚实提示到位：** 「密码无法找回」（本地优先产品的正确姿态）、「演示数据，不代表真实能力」。
- **向导可续装：** 中途刷新页面，sessionStorage 恢复进度，不用从头来。还有「推倒重建」重置入口。
- **0 成员时「创建并分发」按钮正确 disabled**（实测），不会让小白点进去吃错误。
- **完成后 dashboard 给「从第一件事开始」4 个示例 + 一键填入**，解决了「面对空产品不知道干什么」。
- **FirstRunTour 可跳过**，不强制。

这套首次体验，比我审查过的多数同类项目好。

### 6.2 【P1】最大的坎：第 3 步接模型

向导 4 步：账号 → 公司 → **模型** → 资料与组织。

**第 3 步是硬门槛，而且跳过有连锁后果：**

- 跳过 → 员工对话回复「尚未绑定任何模型」（`app/setup/page.tsx:111-116,2349`）。小白不知道这是什么意思，只知道「AI 不干活」。
- 第 4 步 AI 生成组织**依赖模型 + 知识库资料**（`org_synthesis.py:196-210`，缺资料直接 400）。所以跳过第 3 步 → 第 4 步也用不了 → 整个向导的价值塌一半。

**而我在第 3 步实测撞到了 3.3 的 httpx bug：** 「拉取模型列表」成功列出 2 个模型，「测试连通」报 `Invalid port: ':1]'`。对小白来说这是**完全无法自行排查**的 —— 他填的 base_url 和 Key 都是对的，错误却指向端口。

### 6.3 【P2】完成页显示过期的失败状态

向导完成页仍然显示那次本地测试失败（`Invalid port`），**而服务端 `/models/diagnostics` 已经返回 `ready=True`**。小白看到「完成」页上有个红色错误，会认为安装没成功。

根因：完成页读的是本地缓存的测试结果，没有重新拉服务端诊断。修法：完成页以服务端 diagnostics 为准。

### 6.4 【P2】内部调研文案泄漏到客户界面

`content/org_presets/pack_sales.json:3`：

```json
"industry": "一人公司·销售岗位包（Lindy $300/月 付费点验证）"
```

这个字符串**出现在向导的组织预设下拉里，客户看得见**。我检查了全部 28 个预设，只有这一个泄漏。

「Lindy $300/月 付费点验证」是内部竞品调研笔记，不该给客户看 —— 它既暴露了你在对标谁，又让客户困惑「这是要收我 300 美元吗」。修法：改成纯业务描述，并加一条测试禁止预设文案出现竞品名 / 价格 / 「验证」字样。

### 6.5 【P3】新装环境体检必报异常

诊断页实测：6 项里 5 项 ✓，1 项 ✗「自动升级通道：未部署 manifest.json」。

这对开发者是正常的（还没发布客户端更新），但**小白看到「1 项异常」会以为产品装坏了**。建议：未发布过更新时显示「未启用（可选）」而不是 ✗ 异常。

### 6.6 小白维度结论

**引导设计是优秀的，但引导的终点（接模型）恰好是全产品最脆弱的一步。** 修掉 3.3 的 `trust_env` 和 6.3 的过期状态，小白体验能从 7.5 提到 8.5。这两处都是小改动。

## 7. 维度五：运营经理（4.5 / 10）—— 最弱的一维

### 7.1 计量与成本护栏：扎实（实测）

这部分是真能用的，先给肯定：

- 六维 Token 聚合（`routes/tokens.py:81-437`）+ 自定义单价 + 流水账，实测有真实数据。
- **预算上限在网关里真的强制执行**（`model_gateway.py:902`），不是只存个数字。
- 计费设置页文案专业：「单价参考主流厂商报价口径（元/百万token）。**历史账单按调用当时的单价快照结算，改价不影响已发生的记录**」—— 这是懂计费的人写的。
- 按公司 / 模型 / 日的用量 + CSV / HTML 账单后端都有（`routes/licensing.py:83-262`）。
- 审计导出 CSV / JSON（`routes/events.py:124-139`）、紧急停止与检查点恢复（`governance.py:815,846`）、登录限流、跨租户 404 —— 治理侧后端齐全。
- 治理页实测可用：改进提案审批闸门（「Agent 改动必须经你批准」）、能力包市场、4 个企业模板（通用 / 项目型 / 创意工作室 / 研究团队）。

### 7.2 【P1】商业化轨道可自助免费升企业版 —— 已实测

**我实际操作了一遍：**

```
GET  /subscription?company_id=…
→ {"plan_code":"trial","status":"TRIALING","limits":{"seats":10,"monthly_tokens":1000000}}

POST /subscription/plan  {"company_id":"…","plan_code":"enterprise"}
→ {"plan_code":"enterprise","status":"ACTIVE","limits":{"seats":null,"monthly_tokens":null}}
```

**一次 POST，无支付、无审批、无 License 校验，试用版直接变企业版 ACTIVE，席位和 Token 配额都变成不限。**

**权限口径要说准确**（我纠正一个容易夸大的说法）：`routes/subscription.py:63` 要求 `Capability.MANAGE`，所以**不是「任何人」能升，是「任何公司的老板」能给自己升**。这不是跨租户越权，是**商业流程缺失** —— 付钱这个环节根本不存在。

配套取证：

- `subscription_service.py:5-6` 注释明写「**金额刻意缺席**」，`PLAN_CATALOG` 里没有任何价格字段。
- **全仓无支付集成**（无 Stripe / 支付宝 / 微信支付）。
- **`seats_limit` / `monthly_token_quota` 只写不读**：grep 全仓，这两个字段只出现在 catalog 定义、写入（`:114/115/154/155`）、序列化（`:188/189/194/195`）和 schema/model 声明里，**没有任何一处拿它们做拦截**。配额是装饰。
- **前端零调用方**：grep `apps/web` 全目录，`/subscription`、`/byok`、`/billing`、`/license` **四个模式全部 0 命中**。

**而 `README:206` 写的是：「Commercial rails：14天试用 + 套餐 + 发票 + BYOK + License」。**

这就是本次审查发现的**最大的「声明与实现不符」**。运营经理如果照 README 去规划商业化，会发现整条轨道是空的。

> 注意区分：**License 机制（Ed25519）是真的闸门** —— 校验失败全局只读（`main.py:284`），席位溢出转审批（`routes/agents.py:190-210`）。它和 subscription 是两套东西。License 真实但续费要换文件 + 重启、无上传 UI（KNOWN_ISSUES #11）；subscription 完全是半成品。

### 7.3 【P1】BYOK 密钥库是只写黑洞

- Fernet 加密是真的（`routes/byok.py:85`），密文存储、只返回密文，姿势正确。
- **但 `decrypt()` 全仓无调用方，`CompanySecret` 无任何消费者**（`services/secret_vault.py:57`）。
- 也就是说：**客户填了自己的 API Key，网关从来不用它。** 网关走的还是服务端 `.env` / 模型配置里的 `api_key_env`。
- verify 端点只报告 `configured`，**不做真实探测**（`:134-148`），所以客户看到「已配置」就以为能用了。

对运营来说这比「没有 BYOK」更糟：**没有**是客户预期管理问题，**有但是假的**是信任问题。客户以为自带 Key 就能用自己的额度，实际上烧的是你的服务端 Key。

修法二选一：① 把 vault 接进网关的 `_resolve_api_key` 优先级链；② 在 UI 和 README 里撤掉 BYOK 声明，标注「即将支持」。**我建议 ①**，因为这是「一人公司」客户最关心的成本自主权。

### 7.4 【P1】公司成员管理无界面

后端有完整的 4 个端点：`GET/POST /companies/{cid}/members`、`PATCH/DELETE /companies/{cid}/members/{mid}`（`routes/members.py:349/385/527/683`），角色矩阵也真的落地了（`core/permissions.py:144-175`）。

**前端零调用方。** grep `apps/web` 全目录，`/members` 只命中 `/projects/{id}/members`（那是项目里的 **AI** 成员，不是公司里的**真人**成员）；搜「邀请 / 成员管理 / 添加成员」只命中静态原型 HTML 和项目页的 AI 成员面板。

后果：

- **老板没法从界面邀请任何人。** 多成员协作只能靠手敲 API。
- 而且后端本身的邀请方式就很原始：`routes/members.py:422-427` 要求老板**手输对方的用户名 + 密码**来创建成员 —— 没有邀请链接、没有邮件邀请。老板得先帮员工想好密码，再线下告诉他。
- `README:72` 还写着「多成员未开放」，**这条已经过期**（后端开放了），但前端确实没开放，所以 README 歪打正着。

对运营来说：**没有邀请链接 = 没有团队扩散 = 没有自然增长。** 这是增长侧最大的缺口。

### 7.5 【P2】账单与流水导出无入口

后端有 `/billing/invoices/export.csv`（`licensing.py:97`）、HTML 账单、事件 CSV/JSON 导出、交付物分组与单文件下载（`routes/delivery.py:64-148`）。

**前端只有交付物下载有入口**，账单和用量流水都没有（实测用量流水 tab 只有刷新按钮）。运营要拿账单给财务，得手拼 URL。

另外**缺批量交付物导出** —— 交付中心只能逐个文件下载，一个项目 20 个文件要点 20 次。

### 7.6 【P2】成本开箱全 ¥0

实测所有费用字段都是 ¥0，因为没配单价。计费设置 tab 确实存在且提示清楚（「还没有配置任何计费标准」），所以**不是无解释的 0**，但仍有两个运营问题：

1. **没有默认参考价 / 一键导入主流厂商报价。** 运营要自己去查每家每百万 token 多少钱再手填。
2. 顶层看板的「总费用 ¥0」只有一行小字「按后台计费标准估算」，老板大概率不会点进 Token 统计的第二个 tab。**开箱即用的成本可见性 = 0。**

### 7.7 增长与可观测：有底子，缺闭环

**有的：** 行业包（28 个预设）、公司作为模板 + 全局能力包市场（`governance.py:268-278,521`）、通知 + Web Push（`routes/notifications.py:90-183`，需 VAPID，真机未验证 #19）、飞书/钉钉/Slack webhook（`services/im_webhook.py`）、超级 Agent 日报（`scheduler_engine.py:208`）、`/health` + `/health/db` 真实 503（`routes/health.py:14-30`）、全链路 request_id（`main.py:196`）、一键诊断、便携启动器预启动快照、备份/恢复脚本 + runbook（`tools/backup.sh`、`restore.sh`、`docs/BACKUP_RUNBOOK.md`）、客户端更新通道（`routes/clients.py`）。

**缺的：** 邀请链接 / 邮件邀请、推荐裂变机制、平台管理员后台（无独立 admin 页）、封禁用户端点（只有成员 suspend）、告警看板（有 Prometheus 规则但无 Grafana 板 #14）。

**半完成的：** 后台执行器是单进程 ThreadPool(4)，任务持久化未做（#4）；Docker 产物从未 `up` 验证过（#12）。

**文档错误：** `README:208` 引用 `docs/备份与恢复.md`，**该文件不存在**（实际是 `BACKUP_RUNBOOK.md`）。

### 7.8 运营维度 Top 3

1. **把 BYOK 接进网关，或者撤掉声明。** 现在客户填的 Key 不用，这是信任级问题。
2. **商业化要么补完（支付 + 配额强制 + 最小账单 UI），要么在 README 里降级为「规划中」。** 现在自助升企业版 + 配额不强制 + 无前端 + README 宣称成品，四件事叠在一起是运营最大的坑。
3. **补成员邀请 UI + 邀请链接。** 没有这个，「一人公司」永远只能是「一人」，团队扩散和自然增长都无从谈起。
