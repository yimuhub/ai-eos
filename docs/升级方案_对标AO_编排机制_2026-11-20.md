## 0. 一页结论

**它真正值得学的不是"276 个 AI 角色"，是"让多 Agent 的产出可被机器验收"这一套闭环。** 角色数量是营销面，验收闸门才是它的工程面。

一句话战略：**我们的引擎骨架比它完整，缺的是出口的质量门禁和返工的颗粒度。**

### 我们已有的（不是从零开始）

| 能力 | 我们的现状 | 证据 |
|---|---|---|
| DAG 执行 | 已有，DB 持久化 + 租约锁 + CAS 状态迁移 | `workflow_runtime.py:337 advance_execution` |
| 节点类型 | 12 种，含 APPROVAL / HUMAN_INPUT / SUB_WORKFLOW / HTTP / TOOL / TRANSFORM，比它的 4 种多 | `models/workflow.py:18-33` |

| 验收标准 | **只有任务级**（`mission.acceptance`），且只拼进提示词，没有任何校验 | `models/ceo.py:51`、`workflow_authoring.py:205-217` |

### 我们缺的五件事（按价值排序）

| # | 机制 | 它的做法 | 我们的差距 | 价值 |
|---|---|---|---|---|
| 1 | **步骤级验收闸门** | `acceptance` + `assert`（纯函数断言），未过定向返工一轮，仍不过则该步失败 | 无。`execute_step`（`:133`）拿到 output 直接 `_finish_step` | ★★★★★ |

| 3 | **返工三粒度** | 整轮重跑 / 从某步重跑 `--from` / 带意见在原稿上改 `--feedback`，下游自动级联 | 只有整轮重跑 | ★★★★☆ |

单人约 5 周；两人并行约 3 周。**不建议一次全做**，按 §5 的四批顺序推进，每批独立可验收。

## 1. 它的真实分层：护城河在校验层

README 和它的宣传页几乎都在讲角色数量与"一人公司"。但从 Schema 和 CLI 参数反推，它的真实结构是五层：

```
L1 声明层    workflow.yaml + schemas/workflow.schema.json + yaml-language-server 补全
L2 执行层    DAG 自动并行、指数退避重试、超时 x1.5 递增、断点续跑
L3 校验层    acceptance（模型审内容） + assert（脚本审结构） + 定向返工 + 缺件不放行
L4 资产层    角色库 / team loadout / prompt lab / skill 方法论
L5 交付层    ao-output/ 目录、report.html 单文件、export docx/pdf/pptx、--notify、ledger
```

**关键洞察：#1 到 #2 我们都有，还更强；#3 我们是 0。** 而 #3 恰恰是"AI 团队"能不能被老板信任的分水岭——没有闸门，多 Agent 只是"多写了几段话"。

它的 EVAL_FINDINGS 里有一句很诚实的话：DeepSeek 这一档模型上多智能体明显优于单次 prompt，但本地 8B 级小模型多角色交接会放大漂移、产出反不如单次。**这条结论本身就是它最值钱的东西**——它给了"什么时候该用多 Agent"的边界，而不是假装永远更好。我们也要有这个边界（§2.5）。

## 2. 六项机制，逐项拆解

### 2.1 步骤级验收闸门（最高优先级）

#### 它怎么做的

YAML 里每个 step 可挂两个字段，语义严格分开：

```yaml
steps:
  - id: summary
    role: "product/product-manager"
    task: "综合反馈输出结论：{{tech_report}}{{design_report}}"
    acceptance: "1. 明确给出通过/不通过结论 2. 列出必须解决的问题"   # 注入 prompt，并作为评审依据
    assert:                                                          # 纯函数，不过模型
      emits_files: 6          # 产出里必须恰好 6 个文件块
      min_bytes: 2000         # 防截断
      matches: { "^## ": 6 } # 正则命中次数
      contains: ["## 验收清单"]
```

执行语义：

1. 先跑 `assert`（不花钱、不调模型）；
2. 过了 assert 且配了 `acceptance`，再让评审模型按 acceptance 打分；
3. 未过 → **定向返工一轮**（把"上一版产出 + 未过项清单"交回同一个角色，只修不过的，不重写）；
4. 仍不过 → 该步失败，标记缺件，产物不放行。

#### 我们的现状

`mission.acceptance` 是有字段的（`models/ceo.py:51`），也确实进了提示词（`workflow_authoring.py:205-217`）。但这只是"告诉模型要达标"，**没有任何代码去检查它是否达标**。`execute_step`（`workflow_runtime.py:133`）在 AGENT 节点返回 output 之后，径直 `_finish_step(COMPLETED)`。

结果就是：模型说"我已经满足了验收标准"，我们就信了。

#### 我们的设计

**核心原则：机械断言先跑，模型评审后跑。** 机械检查零成本，能挡掉 60% 以上的糊弄；模型评审贵，只用于内容质量这类无法形式化的部分。

新增 `app/gates/`（三个文件，全部纯逻辑，可单测、无网络）：

| 文件 | 职责 |
|---|---|
| `rules.py` | 断言规则注册表 + 求值函数，输入 `(output_text, output_files, ctx)` → `Check[]` |
| `judge.py` | 评审模型调用：strict JSON 输出 `{score, verdict, must_fix[]}`，超时/解析失败一律判 `unknown`（不放行也不误杀，转人工） |
| `step_gate.py` | 编排：机械 → 评审 → 返工 → 落库 |

挂载点只有一处：`execute_step` 拿到 output 之后、`_finish_step` 之前。**不改 DAG 推进逻辑，不改节点类型**，避免动到已稳定的状态机。

节点配置就用现有的 `node.config`（JSON 字段，无需迁移节点表）：

```python
node.config["gate"] = {
    "acceptance": "1. 明确给出通过/不通过 2. 列出必须解决的问题",
    "assert": {"min_chars": 800, "contains": ["## 结论"], "min_citations": 2},
    "max_rework": 1,          # 硬上限，默认 1；0 = 只检查不返工
    "on_fail": "fail",        # fail | manual（转人工审批节点）
}
```

新增一张表存证据（审计与复盘都要靠它）：

```
workflow_step_gates
  id, execution_id, node_key, attempt,
  stage          -- 'mechanical' | 'judge'
  checks         -- JSONB: [{rule, expected, actual, passed, detail}]
  passed, blocking_checks, score, judge_model, tokens, latency_ms, created_at
```

#### 机械断言清单（防糊弄是重点）

它的 `min_bytes` 有个明显漏洞：**凑字数就能过**。我们加三条它没有的：

| 规则 | 语义 | 为什么必须有 |
|---|---|---|
| `min_chars` | **去空白、去 Markdown 标记后的有效字数** | 防用空行/表格线灌水 |
| `max_duplicate_ratio` | 重复句/段占比上限（默认 0.15） | 防"换个说法重复三遍" |
| `not_contains` | 禁用语料（"作为AI"/"我无法"/"以下是"/"综上所述"套话开头） | 防模板腔 |
| `min_citations` | 外部来源计数（URL 或 `来源：` 标记） | 防无依据断言 |
| `emits_files` | 产出文件块**精确**数量（少一个即不过） | 对应"缺件不放行" |
| `json_schema` | 结构化产出按 schema 校验 | 下游要消费 JSON 时唯一可靠的门 |

完整规则集见附录 B。

#### 返工的措辞是关键

"定向返工"和"重跑"的区别全在提示词。我们的返工模板固定为三段，不许模型发挥：

```
你在上一轮产出的基础上修改，不要重写。
【上一版产出】
{previous_output}

【未通过的检查项】
- min_chars：实际 412 / 要求 ≥ 800
- contains「## 核心需求」：未命中
- min_citations：实际 0 / 要求 ≥ 2

只修这些。其余内容、结构、结论保持原样。
```

配套：返工按"新 attempt"记录（沿用现有 `WorkflowStep.attempt` 自增），不覆盖原稿，便于对比"第几轮把问题修掉的"。

#### 成本控制

- `max_rework` 硬上限 1，且返工**不再跑评审模型**（只复跑机械断言 + 一次评审）；
- 一步的 gate 成本 = 1 次评审（约几千 token），机械检查 0；
- 单次执行累计 gate 成本超过预算（默认执行的 `budget_tokens` 5%）→ 停止评审，只跑机械，并在报告里标 `degraded: true`。

#### 验收标准

1. 造 3 个故意缺件的用例（少 1 个文件块 / 字数不足 / 无引用），全部被拦且不进入 END 节点；
2. 造 1 个"凑字数"用例（1000 字但有效字 300、重复率 40%），被 `min_chars` + `max_duplicate_ratio` 拦下；
3. 正常产出通过率不下降（用现有回归集跑，误杀率 0）；
4. 返工只发生 1 次，token 增量 < 单步平均的 1.5 倍。

### 2.2 声明式工作流契约

#### 它怎么做的

一个工作流 = 一个 YAML 文件。配套三件事：

1. **Schema**：`# yaml-language-server: $schema=.../workflow.schema.json` 首行，编辑器里字段补全、手误标红；
2. **`ao validate`**：跨字段检查（依赖成环、变量未定义、角色不存在）——这些 Schema 查不出来，必须靠语义校验器；
3. **export**：`--export skill / plan`，把工作流导出成给编码 Agent 的指令。

关键设计：**文件是可分享的契约，运行时另有状态。** 它没有把 YAML 当运行时状态，运行产物落在 `ao-output/<名称>-<时间戳>/`。

#### 我们的现状

工作流全在 `workflow_definitions` / `workflow_nodes` / `workflow_edges` 三张表里（`models/workflow.py`），画布编辑，DB 即真相。优点是并发、权限、审计都天然成立；缺点是**工作流不能入 git、不能跨公司分享、不能给外部 Agent 消费**。

#### 我们的设计

不推翻 DB，加一层"契约视图"：**DB 是运行时真相，spec 文件是交换格式**，双向可逆。

```yaml
spec: v1
key: prd-review
name: 产品需求评审
inputs:
  - {name: prd, type: text, required: true}
steps:
  - id: analyze
    role: product/product-manager      # 角色档案 key，不是员工 id
    task: "分析以下 PRD：{{prd}}"
    output: requirements
    gate:
      acceptance: "给出核心需求清单，并标注信息缺口"
      assert: {min_chars: 600, contains: ["## 核心需求"]}
  - id: tech_review
    role: engineering/architect
    task: "评估技术可行性：{{requirements}}"
    depends_on: [analyze]
    gate:
      assert: {min_citations: 1, min_chars: 500}
```

四件配套产物：

| 产物 | 落点 | 说明 |
|---|---|---|
| `spec/schema.py` | 新文件 | 生成 JSON Schema（`GET /schemas/workflow.schema.json`），供 VS Code / JetBrains 补全 |
| `spec/compiler.py` | 新文件 | spec → 表记录。**编译前必过校验器**，不合法直接 422，绝不半截入库 |
| `spec/serializer.py` | 新文件 | 表记录 → spec。导出要**稳定**（同一定义两次导出字节一致），否则没法进 git diff |
| `spec/validator.py` | 新文件 | 三层校验：结构（Schema）→ 语义（环/可达/变量/角色存在）→ 策略（节点数 ≤ 24、并发 ≤ N、估算 token 成本） |

接口：

- `POST /workflows/validate`（dry-run，返问题清单，不写库）
- `POST /workflows/import`（带 `dry_run` 开关）
- `GET /workflows/{id}/export?format=yaml|json|skill`
- `GET /schemas/workflow.schema.json`

**往返幂等是硬指标**：导出 → 手工改一行 → 导入 → 再导出，两次导出必须字节一致（除 `updated_at` 类字段）。做不到就是隐式状态没清干净，这是最容易埋雷的地方。

#### 为什么不学它的"全文件态"

它是单机工具，一个用户一个目录，文件态没问题。我们是多租户：文件态意味着并发编辑冲突、权限绕过、审计断链。**契约文件只做出入口，绝不做真相源。**

#### 验收标准

1. 现有全部工作流（含 CEO 生成的历史版本）可导出为合法 spec，`validate` 全过；
2. round-trip 幂等（导出→导入→导出，字节一致）；
3. 环 / 未定义变量 / 不存在的角色 / 节点超限，四类错误各自给出可定位到 step id 的中文报错；
4. Schema 在 VS Code 里能补全 `gate.assert.*` 字段。

### 2.3 角色档案与员工解耦 + 阵容锁定

#### 它怎么做的

- **角色库**是能力条目（`agency-agents-zh` 276 个），与"谁在哪个公司上班"无关；
- **Team / Loadout**：`ao team save <workflow.yaml>` 把阵容抽出来存成 `~/.ao/teams/*.team.yaml`；`ao run --team <名字>` 时把可选角色**锁定**为这几个，所以"既不会漏人、也不会幻觉出别的角色"。

这句话很关键：**锁定是防幻觉的手段，不是偷懒的捷径。** 我们现在的 CEO 每次都重新规划，模型偶尔会找一个不存在的岗位，或者漏掉财务视角。

#### 我们的现状

员工档案（`models/agent.py`）绑定公司/部门/上级/模型，是"实例"；`expert_packs/` 是行业包，里面是专家定义，但没有独立成"可跨公司复用的能力条目"，也没被工作流引用。

#### 我们的设计

拆成两层：

```
role_profile（能力条目，跨公司可复用，可版本化）
   id, key, domain, capability_tags[], system_prompt,
   default_gate(jsonb), model_tier, version, source(pack/self/custom)
        ↓ 实例化
agent（员工，公司内实体，已有表）
   + role_profile_id（nullable，老数据可空）
```

- `default_gate` 是这个角色的**出厂验收标准**。比如"财务分析师"默认要求 `json_schema` + `min_chars 500`；工作流不写 gate 时自动继承，写了则覆盖。这是它没有、但对 B 端特别有用的一点：**质量标准随角色走，不随工作流走。**
- 行业包 = role_profile 集合 + 提示词基线，天然落在我们已有的 `expert_packs` 上，不新造概念。

阵容锁定：

```
team_loadouts(id, company_id, name, role_profile_ids jsonb,
              default_inputs jsonb, created_by, created_at)
```

- `POST /teams/save`：从一次执行抽出实际参与的角色；
- 组合规划时把候选集合**限定**在 loadout 内，提示词里明确"只能从这 N 个角色里选"；
- loadout 存的是**角色 key 不是员工 id**——换公司、换员工也能复用，这是它做对的地方。

#### 验收标准

1. 同一 loadout 跑 10 个不同任务，角色集合始终等于 loadout（0 漏人、0 幻觉角色）；
2. 老员工数据迁移后 `role_profile_id` 为空仍可正常运行（不破坏现有）；
3. 同一 role_profile 在两家公司被实例化，各自模型绑定独立。

### 2.4 返工三粒度

#### 它怎么做的

| 粒度 | 命令 | 语义 |
|---|---|---|
| 整轮 | `ao run wf.yaml --resume last` | 只重跑失败步骤 |
| 从某步 | `--resume last --from marketing_plan` | 该步及其下游重跑，上游复用 |
| 带意见 | `--from write_story --feedback "结尾太平淡"` | 把"上一版产出 + 意见"交回同一角色，**在原稿上改**，下游自动重跑 |

第三种的措辞是它的精髓：`--resume --from` 是"让他重做"，`--feedback` 是"让他改"。人跟下属沟通就是这么分的。

#### 我们的现状

`workflow_runtime.py` 有执行级 pause/resume/cancel/retry，**没有步骤级返工，也没有"在原稿上改"**。用户在任务详情里看到某一步不满意，只能整个重跑，前面的 token 全白烧。

#### 我们的设计

三步：

**① 步骤级重跑**：`POST /executions/{id}/rework {node_key, mode: "rerun"}`。把 `node_key` 及其所有下游标 `STALE`，其余步骤的输出作为 ctx 种子复用。复用现有 `WorkflowStep.output_data`，不新建表。

**② 带意见返工**：`mode: "revise"`，构造 prompt 为 `原任务 + 上一版产出 + 用户意见 + 约束"在原稿上修改，不要重写"`。落库时 `attempt+1`、`revised_from=上一版 step_id`，原稿保留。

**③ 下游失效的准确传播**（最容易做错的地方）：不能简单地"把下游全部标脏"，否则 A→B、A→C、B→D、C→D 这种菱形依赖会重复跑 D。

正确做法：

- 每个 `WorkflowStep` 落库时记录 `input_signature`（所用上游输出 + 节点配置的 sha256）；
- 返工完成后，从 `node_key` 出发做拓扑遍历，**只有 input_signature 变了的步骤**才标 `STALE`；
- D 的上游 B、C 若都变了，D 的 signature 变一次，只跑一次。

这套签名机制顺带解决另一个问题：**幂等**。签名没变的步骤即使被调度到也不重跑，省 token且可审计。

#### 验收标准

1. 菱形依赖下改 A，D 只跑一次（用 trace 计数验证）；
2. 改一步（`marketing_plan`）后，上游步骤 token 消耗为 0；
3. `revise` 模式下产出与原稿的 diff 只落在被指出的问题上（人工抽检 5 例）；
4. 返工后所有历史 attempt 可查、可对比、可回滚到上一版。

### 2.5 质量证据链

#### 它怎么做的

- `--compare`：跑完再跑一次"单次 prompt 基线"，然后**双向盲评**（A/B 顺序互换评两次，不一致判平），结论与两份完整产出存进 `compare.md`；
- `EVAL_FINDINGS.md` 公开结论：强模型（DeepSeek 档）多智能体明显更优；本地 8B 小模型多角色交接会放大漂移，反不如单次。

#### 我们的现状

无基线、无盲评、无回归评测集。所有"多 Agent 更强"的说法都不可证。这是**销售侧也是工程侧的硬伤**：客户问"你这套比单次问 GPT 强在哪"，我们答不出数字。

#### 我们的设计

```
eval_runs(id, suite_key, case_key, model_tier, workflow_id,
          baseline_kind        -- 'single_agent' | 'manual'
          blind_order          -- 'A_first' | 'B_first'
          rubric               -- JSONB: 维度与权重
          scores               -- JSONB: {A:{...}, B:{...}}
          verdict              -- 'multi_better' | 'tie' | 'baseline_better'
          tokens, cost, latency_ms, created_at)
```

四件事：

1. **固定评测集**：8 个任务 × 3 档模型（强/中/本地小模型）。任务要覆盖我们的真实场景：行业调研、方案评审、内容生产、数据核对。
2. **双向盲评**：评审模型不知道哪份是多 Agent 产出；A/B 互换评两次，两次结论一致才采纳，否则 `tie`。这条它做对了，必须抄机制。
3. **确定性维度优先**：能用规则打分的（是否给出结论、是否有引用、缺件数、字数）先算，模型只打"可读性/洞察力"这类主观分。降低评测本身的方差。
4. **防退化回归**：`tools/run_eval.sh`，任何提示词/编排/闸门规则改动，先跑基线。**评测不过不许合并。**

这套东西的对外价值：给出我们自己的"边界声明"——哪档模型适合多 Agent、哪档建议单 Agent、哪些任务类型多 Agent 反而更差。和它一样诚实，但用的是我们自己的数据。

#### 验收标准

1. 8×3 评测报告产出一份，含每档模型的 `multi vs single` 胜率与 token 成本对比；
2. 双向盲评重复跑 3 次，`verdict` 稳定率 ≥ 80%；
3. 故意改坏一个提示词，回归能捕获（至少 1 个 case 从 `multi_better` 掉到 `tie`/`baseline_better`）。

### 2.6 交付出口：报告、账本、通知

三项低风险高感知，放最后一批。

**① 单文件 HTML 报告**：`GET /executions/{id}/report.html`。要求：内联全部 CSS、零外链、零 CDN、断网双击可开；内容为"专家分工时间线 + 每步产出 + 验收结果表 + token/耗时 + 缺件标注"。它的这个设计对客户演示极其友好——不用装任何东西就能发群里。

## 7. 四个最容易做错的坑

1. **只判长度**。它的 `min_bytes` 就是反面教材。必须配 `min_chars`（有效字）+ `max_duplicate_ratio` + `not_contains`，否则模型学会"写长废话"。
2. **断言过严误杀**。第一次上线建议 `max_rework: 0`（只观察不返工），跑一周收集"本该过却被拦"的样本，再开返工。直接开闸会炸掉正常业务。
3. **返工不设上限**。模型有时会越改越差。硬上限 1 轮 + 预算闸（执行级 5% token），超了转人工。
4. **YAML 与 DB 双写**。一旦允许"改文件直接生效"，就必然出现"文件改了但库里没改"的分裂。**导入是显式动作，导出是只读动作，文件永不自动落库。**

```yaml
      acceptance: "每个角度须说明与同类内容的差异点，不得只写标题"
      assert:
        min_chars: 400
        matches: {"^### ": 3}
        not_contains: ["作为AI", "以下是"]

  - id: draft_a
    role: content/writer
    task: "按第一个角度写初稿：{{angles}}"
    depends_on: [angle]
    output: draft_a
    gate:
      assert: {min_chars: 1200, max_duplicate_ratio: 0.15, min_citations: 2}

  - id: draft_b
    role: content/writer
    task: "按第二个角度写初稿：{{angles}}"
    depends_on: [angle]
    output: draft_b
    gate:
      assert: {min_chars: 1200, max_duplicate_ratio: 0.15, min_citations: 2}

  - id: pick
    role: content/editor
    task: "对比两稿，选一稿并给出修改清单：{{draft_a}}\n{{draft_b}}"
    depends_on: [draft_a, draft_b]
    output: chosen
    gate:
      acceptance: "必须明确选哪一稿，并列出 ≥3 条具体修改项"
      assert:
        json_schema:
          type: object
          required: [pick, fix_list]
          properties:
            pick: {enum: [A, B]}
            fix_list: {type: array, minItems: 3}

  - id: final
    role: content/editor
    task: "按修改清单定稿：{{chosen}}"
    depends_on: [pick]
    output: final
    gate:
      acceptance: "定稿须体现修改清单中的每一条"
      assert: {min_chars: 1500, contains: ["## 结语"]}
```

注意 `policy.max_nodes` 与 `budget_tokens`：这是它没有、我们必须有的**策略层校验**——多租户下不能让一个工作流把公司月度额度烧光。

## 附录 B：断言规则全集（v1）

| 规则 | 参数 | 阶段 | 说明 |
|---|---|---|---|
| `min_chars` | int | 机械 | 去空白/去 Markdown 标记后的有效字数 |
| `max_chars` | int | 机械 | 上限，防灌水 |
| `min_headings` | int | 机械 | Markdown 标题数量下限 |
| `contains` | string[] | 机械 | 必须出现的字面串（多行默认） |
| `not_contains` | string[] | 机械 | 禁用语料 |
| `matches` | {pattern: count} | 机械 | 正则命中次数，`0` 表示"必须不出现" |
| `max_duplicate_ratio` | float | 机械 | 重复句/段占比上限，默认 0.15 |
| `emits_files` | int | 机械 | 产出文件块精确数量 |
| `min_file_bytes` / `max_file_bytes` | int | 机械 | 单文件大小区间 |
| `json_schema` | object | 机械 | 结构化产出按 JSON Schema 校验 |
| `min_citations` | int | 机械 | 外部来源计数 |
| `min_source_domains` | int | 机械 | 不同来源域名数（防同一链接刷引用） |
| `min_table_rows` | int | 机械 | 表格数据行下限 |
| `acceptance` | string | 评审 | 交评审模型按条打分，需返回 `must_fix` |
| `judge_threshold` | float | 评审 | 默认 0.6，低于即不过 |
| `custom` | script_id | 机械 | **白名单**内已注册的纯函数，禁止任意执行 |

规则求值统一签名：`(output_text, output_files, ctx) -> {rule, expected, actual, passed, detail}`。**全部可单测，全部无网络。**
