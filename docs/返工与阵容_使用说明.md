# 步骤级返工与阵容锁定 使用说明

> 版本：M3（2026-11-20）｜实现：`app/workflow_runtime.py`、`app/api/routes/teams.py`｜迁移：`0031`、`0032`

## 一、步骤级返工

### 一句话

跑完发现某一步不行，不用整轮重来：**上游一行不重跑，下游按"输入指纹"决定谁该重做**。

### 为什么需要

此前只有执行级的暂停/继续/取消。用户看到"第 3 步写得太平"，唯一办法是整轮重跑——前两步的模型 token 全白烧，而且重跑结果还可能不如上一版。

### 三种粒度

| 粒度 | 请求 | 语义 |
|---|---|---|
| 整轮 | `POST /executions/{id}/rework {"mode":"rerun"}` | 从 START 重跑，所有步骤作废 |
| 从某步 | `{"node_key":"marketing_plan","mode":"rerun"}` | 该节点重做；上游复用；下游按指纹判断 |
| 带意见改稿 | `{"node_key":"write_story","mode":"revise","feedback":"结尾太平淡"}` | 把**上一版产出 + 意见**交回同一个员工，在原稿上改 |

`revise` 与 `rerun` 的区别全在提示词。改稿模板固定三段，不许模型自由发挥：

```
【上一版产出】
<上一版正文，超过 8000 字截断>
【需要修改的地方】
<用户意见，超过 4000 字截断>
【要求】只针对上述问题在原稿上修改，其余内容、结构与措辞保持原样；
输出修改后的完整版本，不要解释你改了什么，也不要新增未被要求的内容。
```

任务标题会加 `（改稿）`，任务中心能一眼分出"首跑 / 改稿 / 闸门返工"。

### 下游失效：靠指纹，不靠"全标脏"

最简单的做法是"把该节点的所有下游标脏"，但菱形依赖会重复执行：

```
        A
       / \
      B   C
       \ /
        D
```

改 A 若把 B、C、D 全标脏，B、C 跑完后 D 会被两条边各调度一次——重复建任务、重复计费。

实际实现：

1. 每个步骤完成时记录 `input_signature` = `sha256(节点类型 + 配置 + 直接上游产出 + 返工指令)`；
2. 返工时只把**目标节点**的历史完成记录打上 `stale_at`；
3. 推进时每个"花钱/有副作用"的节点（AGENT / HTTP / TOOL / TRANSFORM / SUB_WORKFLOW / CONDITION）先算本次指纹，与历史步骤比对：
   - 指纹一致 → 复用旧产出，不执行（0 token）；
   - 指纹不同或没有可比记录 → 执行，写新 attempt；
4. 复用节点仍会把后继排进队列，让下游**被重新评估**一次——所以 D 的指纹只算一次，只跑一次。

由此得到三条可测性质：

- 改中间一步，上游步骤调用次数 +0；
- 改一步且新产出与旧产出相同，下游调用次数 +0；
- 菱形依赖下改 A，D 恰好执行 1 次。

### 状态与安全

- 只有"停了"的实例能返工：`COMPLETED / FAILED / PAUSED / WAITING_INPUT / WAITING_APPROVAL`；`RUNNING` 返回 409（避免两拨 worker 抢同一批节点）。
- 状态迁移用 CAS，已取消的实例不会被返工"复活"。
- `START / END` 不支持步骤级返工（没有意义，且会破坏终态判断）。
- 历史 attempt 全部保留：旧版本 `stale_at` 非空、产出可查，可对比、可回滚（回滚 = 对旧版本再做一次 rerun）。

### 接口

```http
POST /executions/{eid}/rework
Content-Type: application/json

{"node_key": "b", "mode": "rerun", "feedback": null}
```

返回 202：`{"detail":"rework started","node_key":"b","mode":"rerun","full_rerun":false}`，执行在后台推进。轮询 `GET /executions/{eid}` 看新 attempt。

错误：400（mode 非法、START/END、revise 缺 feedback）、404（节点不存在）、409（实例还在跑）。

## 二、阵容锁定（Loadout）

### 一句话

把跑得好的阵容存下来，**存的是角色 key 不是员工 id**；导入新流程时锁定候选集合，防漏人、防幻觉岗位。

### 两层结构

```
role_profiles（角色档案 / 能力条目）
   key, name, domain, capability_tags, system_prompt, default_gate, model_tier
        ↓ 实例化（可空，老数据不受影响）
agents.role_profile_id
        ↓ 打包
team_loadouts（阵容）
   name, roles=[{key, name}], default_inputs
```

`default_gate` 是这个角色的**出厂验收标准**（例如财务分析师默认要求 `min_chars ≥ 500`）。自 M6 起会自动继承，规则见下节。

### 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET / POST | `/role-profiles?company_id=…` | 列 / 建角色档案（key 公司内唯一） |
| GET / POST | `/teams?company_id=…` | 列 / 建阵容（`role_keys` 必须都存在） |
| GET | `/teams/{id}` | 单个别阵容 |
| POST | `/teams/from-execution` | 从一次执行抽阵容：没绑档案的员工就地补一个（key 由姓名生成） |

### 锁定怎么生效

`POST /workflows/import` 增加可选字段 `loadout_id`：

```json
{"spec": "...", "loadout_id": "…"}
```

带该字段时，spec 里每个 AGENT 节点的 `agent` 必须匹配阵容里的角色名，否则返回 422，`issues` 里带 `agent_not_in_loadout` 与 `nodes[i].agent` 定位。`dry_run` 同样受约束。

### 出厂闸门继承（M6）

规则只有三条，都在 `app/gates/inherit.py` 里：

1. **节点显式 gate 永远优先**，继承只在 `config.gate` 缺失时发生；
2. 继承来的闸门**强制 `on_fail=observe`、`max_rework=0`**。角色档案改一次会影响所有继承它的流程，不能让"建议标准"直接阻断生产；观察一轮误杀率后再到具体节点写 `fail`；
3. 档案里**不认识的断言名直接丢掉**（例如 `min_words`），配置写错不该让流水线卡死。

生效位置：`POST /workflows/import`（响应里多一个 `gates_inherited`，说明补了几个）与 CEO 生成流程。两者的清洗逻辑是同一份函数，不各写一套。

### CEO 统筹接阵容（M6）

`POST /ceo/missions` 增加可选字段 `loadout_id`：

```json
{"company_id": "…", "instruction": "…", "loadout_id": "…"}
```

行为：

- 创建统筹时**先验阵容归属**（不存在或不属于本公司 → 404），再花模型调用去拆解；
- 生成工作流时，任何 AGENT 节点引用了阵容外员工 → **不生成工作流**（返回 `None`），任务照常跑，原因写进日志与 `meta.errors`。不做"静默改派给别人"——那等于让锁定变成摆设；
- 带阵容的统筹**不复用旧版工作流**（旧版可能是别人生成的、阵容外的员工）；
- 阵容没有绑定任何员工时明确报错（`阵容没有绑定任何员工`），不返回空集合静默放行；
- 不传 `loadout_id` 时行为与历史完全一致（`ceo_missions.loadout_id` 为 NULL）。

### 已知限制

- 角色档案按公司隔离（多租户下不做跨公司全局表）；"跨公司复用"目前靠导出/导入 spec 实现。
- 阵容锁定接入了 **spec 导入** 与 **CEO 统筹生成**；执行期的临时改派（如 coworker 接管）仍不受锁约束。
- 员工与角色档案的绑定目前由"从执行抽阵容"自动补，没有单独的绑定管理页。
- 继承的闸门是观察态，**不会阻断**。要真正拦，需要在节点上显式写 `on_fail: fail`——这是有意的两步走。
