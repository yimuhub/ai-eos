# 质量评测集（B6）

目标：让「AI 员工交付质量」可度量、可随版本回归。用一组真实业务任务走现有主链路
（建任务 → 启动 → 轮询 → 取产出），再用**可机检的规则**打分。

边界先说清楚：

- 只做**规则评分**，不调用第二个模型做 LLM judge，避免评测依赖第二套模型与额外费用。
- 规则能检查「有没有结论、有没有风险、是否给了引用、结构够不够、有没有禁用话术」，
  **不能**判断事实是否真实正确；引用只检测特征，不校验来源权威性。
- 本机没有真实模型密钥，因此仓库当前**没有真实模型基线**，详见文末。

## 文件

| 文件 | 用途 |
| --- | --- |
| `tools/eval_tasks.seed.json` | 60 条真实任务种子（5 类 × 12 条） |
| `tools/eval_harness.py` | 评测器：下发任务、轮询、规则评分、出报告 |
| `apps/api/tests/test_eval_harness.py` | 评分器自测 + 种子集结构护栏 |
| `docs/评测集.md` | 本文档 |

## 本机可验证的部分（无需 Key）

```bash
# 1) 评分器自测：内置好/中/差样本，断言排序与规则生效
python3 tools/eval_harness.py --self-test

# 2) 看看会跑哪些任务，不发任何请求
python3 tools/eval_harness.py --dry-run

# 3) 护栏测试
cd apps/api && .venv/bin/python -m pytest tests/test_eval_harness.py -q
```

`--self-test` 通过时退出码为 0；`--dry-run` 只读种子集并打印任务与规则。

## 真实评测怎么跑（需要 Key）

### 1. 准备一个可丢弃的服务实例

不要让评测写入真实库 `apps/api/data/aieos.db`。推荐用临时 SQLite 起一个独立实例：

```bash
cd apps/api

export DATABASE_URL="sqlite+aiosqlite:////tmp/aieos_eval.db"
export STORAGE_DIR="/tmp/aieos_eval_storage"
export JWT_SECRET="$(python3 -c 'import secrets; print(secrets.token_hex(32))')"
# 真实模型密钥放在环境变量里，由模型配置的 api_key_env 指向它
export EVAL_MODEL_KEY="sk-..."

.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

然后在另一个终端（或已有开发实例上）配置真实模型：

1. 注册 / 登录，拿到 `access_token`；
2. 创建公司，记下 `company_id`；
3. 创建至少一名 AI 员工，并绑定一个可用模型（`POST /agents/{id}/models`）；
4. 确认 `/models/diagnostics` 的 `ready` 为 `true`。

```bash
TOKEN="$(curl -s http://127.0.0.1:8000/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"identity":"you@example.com","password":"your-password"}' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["access_token"])')"

COMPANY_ID="$(curl -s http://127.0.0.1:8000/companies \
  -H "Authorization: Bearer $TOKEN" \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)[0]["id"])')"
```

### 2. 跑评测

```bash
python3 tools/eval_harness.py \
  --base-url http://127.0.0.1:8000 \
  --token "$TOKEN" \
  --company-id "$COMPANY_ID"
```

也可以把凭据放进环境变量，避免出现在 shell 历史里：

```bash
export AIEOS_EVAL_TOKEN="$TOKEN"
export AIEOS_EVAL_COMPANY_ID="$COMPANY_ID"
python3 tools/eval_harness.py --base-url http://127.0.0.1:8000
```

可选参数：

| 参数 | 说明 |
| --- | --- |
| `--agent-id` | 指定执行员工；默认自动选一个已绑定模型的员工 |
| `--tasks` | 任务种子路径（默认 `tools/eval_tasks.seed.json`） |
| `--out` | 报告路径（默认仓库根目录 `eval-report-YYYYmmdd-HHMMSS.json`） |
| `--timeout` | 单条任务等待上限（秒，默认 300） |

每条任务只创建并启动一次。评测器轮询 `GET /tasks/{id}` 到 `COMPLETED / FAILED / CANCELLED`
或超时，取 `result`（为空时回退到最近一次执行输出）参与评分。

**报告与终端输出绝不含 token**；报告里只记录服务地址、公司 id、员工 id 和任务结果。

## 评分规则

每条 `expected` 里的规则逐条检查，**每条规则等权**：

| 规则 | 检查方式 | 示例 |
| --- | --- | --- |
| `must_include: ["结论", "风险"]` | 每个词各算一条；忽略空白与英文大小写后做子串匹配 | 缺少「风险」则这条失败 |
| `forbidden: ["我不确定", "作为AI"]` | 每个词各算一条；命中任一即失败 | 输出「作为 AI」也会命中 |
| `min_chars: 600` | 去掉所有空白后的可见字符数 | 中文正文按实际字数算 |
| `min_sections: 3` | Markdown 标题（`#` 到 `######`）数量，先剔除代码块 | 至少要 3 个标题 |
| `citation_required: true` | 命中任一引用特征即可：`[1]`/`[1,2]`、`来源：`、`参考资料`、`参考来源`、`http(s)://` 链接 | 只检测“有没有”，不校验来源质量 |

每条任务的得分：

```
任务得分 = 通过的规则条数 / 规则总条数 × 100
```

任务**通过**的条件更严格：**所有规则全部通过，且任务最终状态为 `COMPLETED`**。
得分 80 但没有引用，仍然算「不通过」——平均分用于观察趋势，通过率用于发布门禁。

报告 JSON 主要字段：

```json
{
  "version": "5.14.0",
  "generated_at": "2026-10-31T12:00:00+00:00",
  "base_url": "http://127.0.0.1:8000",
  "company_id": "...",
  "agent_id": "...",
  "tasks_file": ".../tools/eval_tasks.seed.json",
  "summary": {
    "total": 60,
    "passed": 48,
    "failed": 1,
    "errors": 1,
    "pass_rate": 0.8,
    "average_score": 82.5,
    "target_pass_rate": 0.8,
    "target_met": true
  },
  "results": [
    {
      "id": "research-ai-office-market",
      "status": "passed",
      "score": 100.0,
      "duration_ms": 42000,
      "output_chars": 860,
      "checks": [{"rule": "must_include:结论", "passed": true, "detail": "包含「结论」"}],
      "failures": [],
      "output_preview": "……"
    }
  ]
}
```

## 「成功率 ≥ 80%」怎么算

```
成功率 = 通过任务数 / 任务总数
通过   = 该任务所有规则通过，且任务状态 COMPLETED
```

当前种子集共 60 条，因此**至少 48 条通过**才达标。报告里的
`summary.pass_rate` 与 `summary.target_met` 直接给出结论；评测器退出码：

- `0`：`pass_rate >= 0.8`；
- `1`：低于目标（可用于发布门禁）；
- `2`：参数/种子集/环境错误（未真正开始评测）。

注意：成功率不是平均分。平均分只用于观察质量变化，不能替代通过率。

## 如何新增任务

在 `tools/eval_tasks.seed.json` 的数组里追加一条：

```json
{
  "id": "plan-quarterly-review",
  "title": "季度经营复盘会准备",
  "category": "方案计划",
  "prompt": "下周开季度复盘会，请准备一份材料，覆盖目标完成情况、偏差原因和下一步动作。",
  "expected": {
    "must_include": ["目标", "原因", "下一步"],
    "min_chars": 500,
    "min_sections": 3,
    "forbidden": ["我不确定", "作为AI"]
  }
}
```

约定：

- `id` 全局唯一，必须用「类别前缀-主题」的短横线小写命名：
  调研汇报 `research-`、方案计划 `plan-`、数据分析 `data-`、文案材料 `copy-`、流程清单 `checklist-`；
  护栏测试会校验 id 格式、前缀与 `category` 是否一致；
- `category` 目前固定 5 类：调研汇报、方案计划、数据分析、文案材料、流程清单；
  若要新增类别，同步修改 `apps/api/tests/test_eval_harness.py` 中的类别、前缀映射与「每类 12 条」断言；
- `prompt` 用真实业务口吻，**不要把字数、章节数等答案要求写进 prompt**，
  这类要求只放在 `expected` 里，否则测的是“照抄要求”而不是交付能力；
- `expected` 至少要有两条规则，且只能是上表中的 5 种（避免只用 `min_chars` 注水的任务）；
- 规则里的关键词要选业务上真正重要的词，避免“结论/建议”这类过于容易命中的词单独成条。

改完先跑：

```bash
python3 tools/eval_harness.py --dry-run
cd apps/api && .venv/bin/python -m pytest tests/test_eval_harness.py -q
```

## 如何把结果贴进版本发布

1. 在准备发布的候选版本上跑一次完整评测，保留报告 JSON；
2. 在发布说明 / CHANGELOG 里贴摘要（不要改版本号）：

```markdown
### 质量评测（B6）
- 版本：v5.14.0
- 任务：60 条（5 类 × 12）
- 通过：48/60（80.0%），平均分 82.5
- 耗时：约 6 分钟
- 报告：eval-report-20261031-120000.json
- 未通过：data-funnel-conversion（缺少引用）、copy-homepage-hero（出现禁用表达）
```

3. 报告文件作为发布附件或 CI artifact 归档，便于下个版本对比。
