# 声明式工作流契约（spec v1）使用说明

> 版本：M2（2026-11-20）｜实现：`apps/api/app/spec/`｜测试：`tests/test_workflow_spec.py`

## 一句话

一张工作流 = 一个 YAML/JSON 文件。**文件能进 git、能被代码评审、能被脚本生成、导入后有机器校验**；画布与数据库只是它的运行时形态。

## 为什么需要

此前一张工作流只存在于数据库里（`workflow_definitions` + nodes + edges 三张表的 JSON），带来三个具体问题：

1. **不可评审**：改流程只能在画布上点，改了什么、谁改的、为什么改，diff 里看不出来。
2. **不可复用**：想把一套流程搬到另一个项目/公司，只能重画或复制 JSON，字段名对不上就静默错。
3. **不可生成**：模型或脚本产出的图无法先校验再落库，错了要等跑起来才发现（缺少 END、变量没来源、员工名写错）。

spec v1 把这三件事收口：**单文件 → 三层校验 → 显式导入 → 可回导**。

## 文件长什么样

```yaml
# yaml-language-server: $schema=http://localhost:8000/schemas/workflow.schema.json
spec: v1
key: prd-review
name: 产品需求评审
description: 评审 PRD 并给出结论
inputs:
  - name: prd
    type: text
    required: true
nodes:
  - key: start
    type: START
    name: 开始
  - key: analyze
    type: AGENT
    name: 分析需求
    agent: 产品经理
    task: |
      分析以下 PRD：
      {{prd}}
      输出核心需求、缺口与风险。
    output: requirements
    gate:
      acceptance: 列出核心需求与缺口，每条可核对
      assert:
        min_chars: 300
      on_fail: observe
  - key: end
    type: END
    name: 结束
edges:
  - {from: start, to: analyze}
  - {from: analyze, to: end}
policy:
  max_concurrency: 4
```

首行的 `$schema` 注释让 VS Code / JetBrains 直接获得字段补全与拼写标红（schema 接口免登录、可缓存）。

## 字段

### 顶层

| 字段 | 必填 | 说明 |
|---|---|---|
| `spec` | 是 | 固定 `v1`。版本不对直接拒绝，不做兼容猜测 |
| `key` | 否 | ASCII 标识（`^[a-z][a-z0-9_-]{0,63}$`）。缺失时由名称生成；同 key 再次导入是**新建一版**，不覆盖旧版 |
| `name` | 是 | 展示名，≤300 字 |
| `description` | 否 | ≤2000 字 |
| `inputs` | 否 | 运行入参声明（`name/type/required`），运行时按名字取用 |
| `nodes` / `edges` | 是 | 图。节点 ≤24 个（`MAX_NODES`） |
| `policy` | 否 | `max_concurrency`（≤8）、`budget_tokens`（≤2e6）等运行策略 |

### 节点通用字段

`key`（必填，图内唯一）、`type`（必填）、`name`、`x`/`y`（画布坐标，可省）。

### 各类型专属字段

| type | 专属字段 | 说明 |
|---|---|---|
| `START` / `END` | — | 各恰好一个 |
| `TASK` | `assignee_hint` | 普通任务 |
| `AGENT` | `agent` 或 `agent_id`、`task`（必填）、`output`、`gate` | 执行员工；`task` 里可插值；`output` 是产出别名，供下游引用 |
| `CONDITION` | `keyword` | 命中走 `label` 匹配的边 |
| `PARALLEL` / `MERGE` | `branch_count` | 并行分支数 / 汇聚 |
| `WAIT` | `seconds`（0–60） | |
| `APPROVAL` | `approver_hint` | 人工审批 |
| `HUMAN_INPUT` | `prompt` | 人工输入 |
| `SUB_WORKFLOW` | `workflow_id` 或 `workflow_key` | 二选一；有 key 时优先用 key |
| `HTTP` | `config`（原样透传） | 公网闸门与凭据引用在运行时校验 |
| `TOOL` | `config` | 工具总线调用 |
| `TRANSFORM` | `config` | 模板映射 |

`gate` 的字段与语义见 [验收闸门_使用说明.md](./验收闸门_使用说明.md)。

## 边与分支

**本实现用显式 `edges`，不用 `depends_on`。** 原因：我们的执行器是**边触发**——`depends_on: [A, B]` 的节点会在 A 完成时就被调度，并不会等 B（AO 的 CLI 是顺序执行，所以它可以用依赖列表）。要在本引擎里表达"等齐再跑"，必须显式插入 `MERGE` 节点：

```yaml
nodes:
  - {key: a, type: AGENT, name: 调研, agent: 研究员, task: ...}
  - {key: b, type: AGENT, name: 取证, agent: 分析师, task: ...}
  - {key: m, type: MERGE, name: 汇聚}
edges:
  - {from: start, to: a}
  - {from: start, to: b}
  - {from: a, to: m}
  - {from: b, to: m}
```

条件分支必须给边写 `label`（如 `是` / `否`），否则只是 warning（不阻断），但运行时会因无匹配边而走默认分支。

## 三层校验

| 层 | 查什么 | 例子 |
|---|---|---|
| 结构 | 顶层类型、版本、未知字段、节点/边字段类型、必填 | `nmae` 拼错 → `unknown_field`；`spec: v2` → `bad_version` |
| 语义 | 图是否成立：START/END、可达性、环、悬挂边、变量来源、员工是否存在、子流程是否存在 | 少 END → `missing_end`；`{{draft}}` 引用下游产出 → `var_not_upstream` |
| 策略 | 节点数、并发、预算等上限 | 25 个节点 → `too_many_nodes` |

**结构层只在 `not_object` / `bad_version` 时短路**，其余问题一次性全报，避免"改一个错又冒一个"。

### 错误码

`not_object`、`bad_version`、`unknown_field`、`missing_field`、`dup_key`、`dangling_edge`、`self_loop`、`dup_edge`（warning）、`missing_start`、`missing_end`、`dead_end`、`unreachable`（warning）、`cycle`、`unknown_var`、`var_not_upstream`、`condition_without_label`（warning）、`agent_not_found`、`subflow_not_found`、`too_many_nodes`、`unknown_assert`、`bad_node_type`、`bad_seconds`。

`level=error` 阻断导入，`warning` 只提示。每条都带 `path`（如 `nodes[1].task`），前端可逐条高亮。

## 接口

| 方法 | 路径 | 权限 | 行为 |
|---|---|---|---|
| POST | `/workflows/validate?company_id=…` | OPERATE | 只校验不写库，200 返 `{ok, issues, summary}` |
| POST | `/workflows/import?company_id=…` | OPERATE | 校验通过才落库；有问题 422（`detail` 同 validate 结构）；`dry_run: true` 等价 validate |
| GET | `/workflows/{id}/export?format=yaml\|json` | VIEW | 只读回导，带 `Content-Disposition` 文件名 |
| GET | `/schemas/workflow.schema.json` | 免登录 | 静态 JSON Schema，`Cache-Control: 1h` |

请求体：

```json
{"spec": "<YAML 或 JSON 文本，或已解析的对象>", "project_id": null, "dry_run": false}
```

导入成功返回 `{id, name, key, nodes, edges}`，并写审计事件 `workflow.imported`。

**导入是显式动作，导出不会自动回写数据库。** 文件改了但没导入，库里就不是新版本——这是有意的，避免"文件与库谁是真的"分裂。

## 变量引用（`{{...}}`）

只有 AGENT 节点的 `task` 会做替换，且**仅当 task 里真的出现 `{{...}}`** 时才开启（编译期写入 `config.interpolate`）。存量工作流的 instruction 即使带花括号也逐字不变。

解析顺序：

1. `{{input.xxx}}` → 运行入参（支持 `input.a.b` 下钻）
2. `{{xxx}}` → 先查**产出别名**（节点的 `output`），再查**节点 key**，最后查**输入名**
3. 支持 `a.b.c` 路径（dict/list 下钻），对象/数组按 JSON 文本插入

**取不到时原样保留 `{{xxx}}`**，不替换成空串——配置错误要在产出里肉眼可见，而不是悄悄少一段上下文。

变量名只认 ASCII 标识符（`{{中文名}}` 不算引用，会被原样保留）。校验器会检查引用的来源必须是**上游**：引用下游产出报 `var_not_upstream`，引用不存在的名字报 `unknown_var`。

## 导出的稳定性

导出要能进 git，所以必须**字节稳定**：

1. 节点按 `key` 排序，边按 `(from, to, label)` 排序——不依赖插入顺序；
2. 空值省略，不写 `null`；
3. 坐标整数化（`310.0` → `310`），避免浮点抖动；
4. 不输出内部 id：AGENT 节点导出**姓名**；只有姓名查不到或同公司重名时才补 `agent_id` 消歧；
5. 子流程导出 `workflow_key`（跨公司可复用），只有该工作流没有 spec key 时才退回 `workflow_id`。

由此得到一条可测的性质：**导出 → 导入 → 再导出，两次文本完全一致**（测试 `test_yaml_round_trip_is_byte_identical` 守着）。

## 与画布、自动生成的关系

- 画布保存（`POST /workflows`）仍走原有内部格式，不受 spec 影响；spec 是**并列的入口/出口**，不是替代。
- CEO 自动生成的工作流写入的是内部格式；需要对外交付时用导出接口转成 spec，再交给别人导入。
- 导入一律 `status=PUBLISHED`、`source=import`、`meta` 记 `spec_version / spec_key / inputs / policy / imported_at`，便于事后追溯"这张图是从哪个文件来的"。

## 已知限制

- 单文件 ≤24 节点；超过请拆成子流程（`SUB_WORKFLOW`）。
- 不支持在 spec 里写"依赖列表"，汇聚必须显式 `MERGE`（见上）。
- `HTTP/TOOL/TRANSFORM` 的 `config` 原样透传，spec 层不做深校验；非法配置在运行时报错。
- 循环图禁止（`cycle`）；需要重试语义请用 `gate.max_rework`，不要画回边。
- 导入不覆盖同 key 的旧版本，而是新建一版（`reuse_key` 机制负责版本链）。
