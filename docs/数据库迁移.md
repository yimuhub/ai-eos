# 数据库迁移（Alembic 单一权威）

> Alembic 是唯一 schema 权威。运行时不再 `create_all`，不再手写补列，
> 请求链路也不再执行 DDL。SQLite 便携首启执行迁移；PostgreSQL 启动只校验。

## 1. 启动与部署边界

| 场景 | 行为 |
| --- | --- |
| SQLite 空库 | 自动执行 `upgrade head`，再校验版本和结构 |
| SQLite 已版本化库 | 自动执行剩余迁移，再校验 |
| SQLite 无版本号的完整老库 | 严格比对模型与表结构，完全一致才 `stamp head`；保留业务数据 |
| SQLite 无版本号的不完整老库 | 拒绝自动改表或 stamp；先备份并执行受控迁移 |
| PostgreSQL / 服务器 | 启动只校验；部署脚本必须先显式 `upgrade`，失败立即停止 |
| 已停用的 `apps/api/alembic/` 链 | revision 无法解析时拒绝自动采用，防止错误 stamp |

校验同时检查单一 head、`alembic_version` 和模型结构漂移。任何版本或结构
不一致都会阻止启动，不会静默继续。迁移子进程的错误输出会隐藏数据库口令。

## 2. 统一命令

在 `apps/api` 下执行，目标默认取 `ALEMBIC_DATABASE_URL`，其次取应用配置的
`DATABASE_URL`：

```bash
uv run python -m app.db.migrations upgrade   # 空库/已版本化库升级；严格采用完整老库
uv run python -m app.db.migrations check     # 必须到 head 且无结构漂移
uv run python -m app.db.migrations current   # 只读当前 revision
uv run python -m app.db.migrations upgrade --url sqlite+aiosqlite:////tmp/drill.db
```

PostgreSQL 部署示例：

```bash
cd apps/api
export ALEMBIC_DATABASE_URL='postgresql+asyncpg://user:pass@host/db'
uv run python -m app.db.migrations upgrade
uv run python -m app.db.migrations check
```

`服务器一键部署.sh` 已把迁移和迁移后校验设为硬门禁；任一步失败都会停止部署。
`deploy/Dockerfile.api` 会拷贝 `migrations/`，镜像内具备完整迁移链。

## 3. 模型变更流程

1. 修改 `app/models/` 并在 `app/models/__init__.py` 注册新模型。
2. 用临时库生成新 revision，绝不拿真实库做 autogenerate：

```bash
cd apps/api
uv run python -m app.db.migrations upgrade --url sqlite+aiosqlite:////tmp/aieos_model.db
uv run alembic -x db_url=sqlite:////tmp/aieos_model.db revision --autogenerate -m "describe change"
```

3. 人工审阅生成文件。新增非空列必须有明确回填策略；SQLite 改列/约束使用
   batch；外键在 SQLite batch 中必须命名；破坏性 downgrade 必须可接受。
4. 在临时库验证：

```bash
uv run python -m app.db.migrations upgrade --url sqlite+aiosqlite:////tmp/aieos_model.db
uv run python -m app.db.migrations check --url sqlite+aiosqlite:////tmp/aieos_model.db
uv run python -m pytest -q tests/test_schema_migration.py tests/test_alembic_baseline.py
```

5. 在 PostgreSQL 测试实例重复 upgrade/check，并做一次 downgrade/upgrade 演练。
6. 已发布的 revision（尤其 `0001_baseline.py`）不得改写；只新增 revision。

`0001` 之后的增量迁移必须保持单 head。`test_schema_foundation.py` 会锁定链路，
`test_alembic_baseline.py` 会逐表比较迁移空库与模型的列和索引。

## 4. 老库采用流程

无版本号不代表可以猜测版本。先备份，再对**副本**运行 `upgrade`：

- 结构与当前模型完全一致：工具只写 `alembic_version`，stamp 到 head。
- 存在任何缺表、缺列、类型或约束差异：工具拒绝修改，并打印差异。

不一致时，根据真实旧版本创建新的数据迁移（补值、改类型、重建约束），
在副本上验证后部署。不得手工 stamp 一个并未达到的版本，也不得删除重复历史
来强行建立唯一约束。`0038` 发现重复成果版本号时会停止并列出重复项。

`apps/api/alembic/` 是已停用的历史 PG-only 链，只作参考，不再添加 revision。
旧链库需要备份、比对并制定数据迁移方案；当前工具不会自动 stamp。

## 5. 回滚与演练

回滚可能删列、删表或丢失新版本写入的数据，执行前必须备份：

```bash
cd apps/api
uv run alembic -x db_url=sqlite:////tmp/aieos_drill.db downgrade 0039
uv run python -m app.db.migrations upgrade --url sqlite+aiosqlite:////tmp/aieos_drill.db
uv run python -m app.db.migrations check --url sqlite+aiosqlite:////tmp/aieos_drill.db
```

`downgrade base` 会删除全部业务表，只用于空演练库。`0039` 订单迁移回滚会
移除在线支付字段和 webhook 幂等表，但保留原有离线订单。

## 6. CI 门禁

`.github/workflows/ci.yml` 在 SQLite、PostgreSQL 16 和契约 job 中显式执行
空库 upgrade、结构 check 和重复 upgrade；PostgreSQL 另外执行
`head → 0039 → head`（即 0040 的 downgrade/upgrade）回滚演练。测试夹具也通过 Alembic 建库，不再以
`create_all` 代替真实发布结构。

按项目约定，Actions 仍仅手动触发；本地开发不手动启动流水线消耗额度。
