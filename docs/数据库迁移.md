# 数据库迁移（Alembic 基线）

> 一句话：**运行时行为不变**（`create_all` + `ensure_columns` 兜底照旧）；
> 新增一套 Alembic 基线 `0001`，覆盖运行时 `create_all` 会建的全部 **107 张表**，
> 用来做 schema 的版本化、审计与回滚。

## 1. 当前现状

`apps/api/app/main.py` 的 lifespan 在每次启动时执行：

| 步骤 | 作用 | 边界 |
| --- | --- | --- |
| `Base.metadata.create_all` | 建**缺失的表** / 索引 | 不修改已存在的表 |
| `ensure_columns`（`app/db/migrations.py`） | 给老表补**可空列**（SQLite/PG 幂等） | 不删列、不改类型、不补非空列（会告警跳过） |
| `backfill_superadmin` | 老库补一个超管标记 | 只做一次 `UPDATE` |

这套机制保证"克隆下来就能跑"，但它有两个天然缺陷：

1. **没有版本表**：无法回答"这个库的 schema 对应哪个代码版本"；
2. **只能往前补**：改类型、删列、补非空列、重建索引都做不了，也无法回滚。

## 2. 为什么加 Alembic（但仍不接管启动）

2026-10-31 审查报告的 E4 项：schema 演进不可审计、不可回滚；私有化客户升级后
schema 与代码可能静默错位。Alembic 补的正是"版本 + 可回滚"这两件事。

**刻意不做的事**：不在启动时自动 `upgrade`。启动自动迁移会让"一次失败的迁移"
直接变成"服务起不来"，也会让多个进程同时抢着改表。迁移是**运维动作**，
必须显式执行、可预期、可回滚。

因此职责划分是：

- **SQLite 便携部署**：`create_all` 继续兜底，忘跑迁移也不会起不来；
- **PostgreSQL / 客户现场**：以 `alembic upgrade head` 为准（`create_all`
  不会给已存在的表补列）；
- **Alembic**：唯一的事实来源（schema 快照 + 版本表 `alembic_version`）。

依赖：`alembic>=1.14` 早已在 `apps/api/pyproject.toml` 的 `dependencies` 里
（本机 venv 实测 1.19.1），本次没有新增任何依赖，也不需要联网安装。

### 3.1 目标库怎么选（`migrations/env.py`）优先级从高到低：

1. `alembic -x db_url=...`（脚本/演练用，最明确）
2. `ALEMBIC_DATABASE_URL` 环境变量
3. `alembic.ini` 的 `sqlalchemy.url`（当前是占位符，通常不命中）
4. `app.core.config.settings.database_url`（兜底，让部署脚本裸跑也能工作）

`env.py` 会在 import 应用模型**之前**把解析结果写回 `DATABASE_URL`
（同步 URL 会换成 `sqlite+aiosqlite://` / `postgresql+asyncpg://` 等价形式），
这样迁移进程里任何"顺手的 engine"都指向同一个库，不会误连别的库。

SQLite 下 `render_as_batch=True`：后续改列/加约束会走"建新表→拷数据→换名"，
这是 SQLite 唯一可行的 ALTER 方式。

对部署脚本的影响：`服务器一键部署.sh` 里的 `uv run alembic upgrade head`
现在走的是本基线（SQLite 下可用；此前指向的旧链在 SQLite 会直接报错）。
该步失败仍然只是 `log_warn`，不影响后续启动——与"运行时暂不自动迁移"的边界一致。

### 3.2 基线包含哪些表

`0001` 由空库 `autogenerate` 生成后**冻结**，包含 107 张表。其中 5 张不是定义在
`app/models/`，而是历史遗留地散落在别处，`env.py` 里显式 import 以保证基线完整：

| 表 | 定义位置 |
| --- | --- |
| `runtime_locks` | `app/task_engine.py` |
| `agent_chat_messages` | `app/api/routes/agent_chat.py` |
| `group_chat_messages` | `app/api/routes/group_chat.py` |
| `learning_plans` | `app/api/routes/growth_center.py` |
| `doc_styles` | `app/api/routes/doc_styles.py` |

> 新模型请放 `app/models/` 并在 `app/models/__init__.py` 注册，不要再往路由里塞表。

## 4. 日常：模型改了，怎么加迁移

```bash
cd apps/api

# 1) 准备一个"已到 head"的临时库（不要拿真实库做 autogenerate）
rm -f /tmp/aieos_mig.db
.venv/bin/python -m alembic -x db_url=sqlite:////tmp/aieos_mig.db upgrade head

# 2) 改模型：app/models/xxx.py + 在 app/models/__init__.py 注册

# 3) 生成迁移（diff 只应包含你这次的改动）
.venv/bin/python -m alembic -x db_url=sqlite:////tmp/aieos_mig.db \
    revision --autogenerate -m "add xxx"

# 4) 人工审阅 migrations/versions/<rev>_add_xxx.py
#    - 新增非空列必须给 server_default 或先 nullable 再回填
#    - SQLite 的 ALTER 会被包成 batch 操作，确认数据拷贝逻辑合理

# 5) 在临时库上跑通，并确认"再 autogenerate 没有新 diff"
.venv/bin/python -m alembic -x db_url=sqlite:////tmp/aieos_mig.db upgrade head
.venv/bin/python -m alembic -x db_url=sqlite:////tmp/aieos_mig.db check
# 期望：No new upgrade operations detected.
```

门禁：

```bash
cd apps/api
.venv/bin/python -m pytest tests/test_alembic_baseline.py -q   # 3 passed
.venv/bin/python -m alembic heads                              # 只能有一个 head
```

`test_alembic_baseline.py` 会分别用 `upgrade head` 和 `create_all` 建两个临时库，
逐表比较**列集合与索引集合**。模型改了却忘了加迁移，这个用例会直接失败。

## 6. 老库如何接入（重要，别直接 upgrade）

已经用 `create_all` 跑起来的老库**没有 `alembic_version` 表**。直接
`upgrade head` 会执行基线的 `CREATE TABLE`，撞上已存在的表直接失败。

正确顺序：

1. **备份**（必须）：`tools/backup.sh`，或至少 `cp aieos.db /tmp/...`；
2. **在副本上比对** schema（下表），确认与基线一致；
3. 一致 → `alembic stamp 0001`（只写版本号，不动表）；
4. 不一致 → 先补齐差异（见下），再 stamp；
5. stamp 之后，后续版本升级才用 `upgrade head`。

副本比对（在 `apps/api` 下执行，输出为空才可 stamp）：

```bash
cd apps/api
DB=/tmp/aieos_copy.db
DATABASE_URL="sqlite+aiosqlite:///$DB" .venv/bin/python - <<PY
import app.main  # 与运行时相同的导入面，metadata 才完整
from app.db.base import Base
from sqlalchemy import create_engine, inspect

db = "$DB"
insp = inspect(create_engine(f"sqlite:///{db}"))
have_tables = set(insp.get_table_names())
extra = sorted(have_tables - {t.name for t in Base.metadata.sorted_tables} - {"alembic_version"})
missing_tables = sorted({t.name for t in Base.metadata.sorted_tables} - have_tables)
missing_cols = {}
for t in Base.metadata.sorted_tables:
    if t.name not in have_tables:
        continue
    have = {c["name"] for c in insp.get_columns(t.name)}
    gap = sorted({c.name for c in t.columns} - have)
    if gap:
        missing_cols[t.name] = gap
print("多出的表:", extra)
print("缺失的表:", missing_tables)
print("缺失的列:", missing_cols)
PY
```

**不一致时怎么办**：最常见的是老库缺可空列。先在副本上启动一次应用
（或直接调用 `ensure_columns`），让兜底补列跑完，再重新比对；仍缺的非空列
必须手写一个 revision 补值（先 nullable / `server_default`，回填后再改非空），
不能靠 stamp 蒙混过去——stamp 只写版本号，不会改 schema。

## 7. 升级与回滚命令

```bash
# 升级（目标库必须显式给出，脚本不会猜默认库）
tools/db_upgrade.sh --db /path/to/aieos.db
DATABASE_URL="postgresql+asyncpg://user:pass@host/db" tools/db_upgrade.sh --to 0001

# 回滚
tools/db_downgrade.sh --db /path/to/aieos.db --to 0001
tools/db_downgrade.sh --db /path/to/aieos.db            # 默认 base，会删全部业务表

# 只看 SQL（离线，不连库）
tools/db_upgrade.sh --db /path/to/aieos.db --sql
```

两个脚本都会：打印目标库与当前/目标版本 → 等 3 秒（`AIEOS_YES=1` 跳过）→
调用 `alembic -c apps/api/alembic.ini -x db_url=...`。脚本不会使用仓库默认库
（`apps/api/data/aieos.db`）作为隐式目标。

## 8. 边界与已知风险

1. **运行时暂不自动迁移**。`app/main.py` 未改：不读 `alembic_version`、
   不执行 upgrade。`alembic_version` 目前只服务运维与后续计划。
   SQLite 上忘跑迁移仍能靠 `create_all` + `ensure_columns` 起服务，
   但这**不代表** schema 正确（类型/约束/删列都不会被兜底修正）。
2. **PostgreSQL 未在真实实例验证**。`0001` 是 SQLite 空库 autogenerate 的产物，
   类型均为通用类型（`sa.String/sa.Text/sa.JSON/sa.DateTime`），预期可移植；
   上线 PG 前请在测试实例跑一次 `upgrade head` + `downgrade base`。
3. **旧迁移链 `apps/api/alembic/` 已停用**。那 32 个 revision 是 PG-only，
   基线之外缺列，且 `23e9b97bb927` 在 SQLite 上抛 `NotImplementedError`。
   `alembic.ini` 已指向 `migrations/`；旧目录保留仅作历史参考，不要再加 revision。
   已在旧链 head 的 PG 库**不能**直接 `stamp 0001`（会被误认为 schema 完整），
   需按第 6 节的"不一致"路径补齐差异，或新建库 + 数据搬迁。
4. **`downgrade base` 会删表**。基线 downgrade 是 `drop_table`，数据不可恢复；
   回滚前必须备份。
5. **基线是冻结快照**。不要把新改动追加进 `0001_baseline.py`；
   已 stamp 的老库不会重跑它，改基线只会造成两套 schema。
6. **并行开发**：多人同时改模型时，先 rebase 再生成 migration，避免同一份
   diff 被生成两次（`alembic heads` 出现两个 head 就是分叉信号）。
