### 3.3 【P1】性能页用本地 `now()` 比对 naive-UTC 列 —— 查询窗口偏 8 小时

`apps/api/app/api/routes/performance.py:39` 与 `:61`：

```python
month_start = datetime.now().replace(day=1, ...)   # 本地时区
... TokenUsage.created_at >= month_start           # 列是 naive UTC
since30 = datetime.now() - timedelta(days=30)      # 本地时区
... Task.updated_at >= since30                     # 列是 naive UTC
```

`datetime.now()` 取的是**服务器本地时间**，而 `created_at/updated_at` 存的是 **naive UTC**。东八区下「本月成本」「近 30 天产出」的窗口边界会偏 8 小时——月初/月末、临界 30 天的记录会被算错桶。这与本次修复的创作中心时刻是**同一类病**（显示层 vs 查询层），应统一改用 `datetime.now(timezone.utc)` 去 naive 化比对，或复用 `core/timeutil`。

### 3.4 【P1】RAG 候选截断 `limit(200)` 无 ORDER BY —— 规模上来后检索看运气

`apps/api/app/knowledge_engine.py:96-107`：

```python
q = select(KBChunk).where(KBChunk.company_id == company_id)
...
if limit: q = q.limit(limit)     # 默认 200，没有 order_by
rows = (await db.execute(q)).scalars().all()
```

候选 chunk 在 SQL 层截到 200 条**但没有排序**，取到的是 SQLite 默认顺序（近似 rowid/插入序）的任意前 200 条，再在 Python 里做 bigram 打分。**公司知识库一旦超过 200 块，真正相关的块可能根本进不了候选集**，检索质量随数据增长悄悄退化。建议至少 `order_by(KBChunk.created_at.desc())` 取最新，或按文档热度/命中历史排序；中期接向量检索（代码注释已留替换点）。

## 4. 维度二：产品经理（7.5 / 10）

### 4.1 主线闭环了（本次实测，真实模型）

经典模式完整跑通：**派活（auto_start 分发）→ 员工执行（真实 agnes-3.0-flash）→ 产出文件 → 自动建 Artifact 置待验收 → 老板验收通过 → 交付中心可下载 → Token 统计计量**。11-07 断的「验收闭环」和「创建不启动」两处都接上了，这是「一人公司」最核心的管理动作，现在是真的。

### 4.2 【本次新增并验证】创作中心：图片/视频模型终于能生成

**这是本次走查挖出的最大产品缺口，已当场补齐：** 模型目录早就支持 image/video 分类，但**产品没有任何生成入口**——老板配了图片模型却无处可用。本次新增「创作中心」（`/media`，侧栏不占位、⌘K 搜「创作」直达）：

- 后端 `routes/media.py` 6 个接口 + `media_generations` 表（迁移 0018）+ 10 项单测；选模型→写提示词→图片同步出图、视频提交后异步轮询（页面隐藏自动暂停）；结果自动下载进公司存储，历史可回看/下载/删除。
- **真实验证：** 用 `agnes-image-2.5-flash` 经 API 与界面各出一张图，约 19s 返回，自动入库、可预览可下载。
- **过程中修了两个真 bug：** ① 预览/下载 401——文件接口需 Bearer，`<img src>`/`<a href>` 带不上 token，改用 `fetchBlobURL`→objectURL（与资产页同套鉴权范式）；② 历史时刻差 8 小时——`_out()` 用了 naive `isoformat()`，改走 `core/timeutil.iso_utc` 输出带 Z（提交 `66b1442`，界面实测 21:47 正确）。
- **视频：** 产品路径正确 + 单测覆盖，但上游持续 `503 video_queue_full`，本次未真正出片；上游恢复后即可用，无需改产品。

### 4.3 极客模式三栏形态成熟（本次完整走查）

`/workspace` 单外壳：左栏会话流（约 465px）、中栏聊天（单聊/群聊/会议/作战四 tab）、右栏功能页 iframe（`?app=…&embed=1`，**多 tab 常驻挂载**，非活跃 collapsed 到 0×0，状态不丢）。实测：

### 5.2 【P2】群聊串行偏慢

5 名成员轮流回应实测约 **5 分钟**（每人 36s–1m30s）。对「随手问一句群聊」的重度用户偏慢。可考虑并行发言（带并发闸门）或先给「正在轮流回应」的明确预期——目前已有「仍在等待服务端返回，不是界面卡死」的诚实提示，这点做得好。

### 5.3 【P3】时刻与角色一致性

- **会议纪要时刻显示 UTC：** 标题是本地「会议 22:24」，纪要正文却写「时间：2026-11-09T14:28」（naive UTC 原始串）。与 §3.3 同源，建议纪要生成时也走本地化或带 Z。
- **角色自称模型名：** 内容策划发言「大家好，我是负责内容策划的 **Agnes**」——把供应商/模型名漏进了人设。应在 system prompt 里强化「你是<角色名>，不要自称模型名」。
- **产品名幻觉：** 真实模型抽样里个别产出把「AI-EOS」误写成无关词（如 HVAC）。这是 LLM 通病，不是管道 bug，但会影响交付物的专业感；建议靠知识库 grounding（把公司/产品事实喂进上下文）+ prompt 约束缓解，关键交付物加一道事实校验。
- **群聊进行中计时：** 流式过程中展开的过程面板计时与最终折叠态时长不一致（进行中显示累计值），最终态正确；属 cosmetic。

> AI 产出质量总评（真实模型抽样）：岗位语气贴合、纪要结构化可用，但有人设漏名与产品名幻觉两类瑕疵。**管道是对的，内容质量靠模型与 grounding，产品侧能做的是把事实喂准、把 prompt 约束住。**
