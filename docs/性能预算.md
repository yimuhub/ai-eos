# 性能预算（C7）

本文件说明 AI-EOS 前端的性能预算：哪些指标已经进入 CI、阈值从哪来、本地怎么跑，
以及尚未接入的运行时指标（交互 P95）后续怎么补。

范围只覆盖 `apps/web` 的 Next.js 构建产物。目标是**防倒退**：让明显把包体做大的
改动在合并前变红，而不是追求一次性的极致优化。

---

## 1. 体积预算表

测量环境：2026-10-31，本机 `cd apps/web && npm run build`（Next 14.2.35，默认
production 配置，Node v24.19.0），对 `.next` 产物做 **gzip -9** 后按 KB 统计。
CI 用 Node 20 构建，产物可能有几 KB 的正常差异，已由 10% 余量覆盖。

| 指标 | 基线 (KB) | 阈值 (KB) | 测量方法 |
| --- | ---: | ---: | --- |
| `first_load_js_gzip_kb`（首屏 JS） | 118.43 | 140 | `build-manifest.json` 的 `rootMainFiles` ∪ 首页 `/layout`、`/(main)/layout`、`/(main)/page` 在 `app-build-manifest.json` 中登记的 `.js`，去重后逐个 gzip 求和 |
| `total_js_gzip_kb`（全站 JS） | 610.52 | 680 | `static/chunks/**/*.js` 全部文件 gzip 求和（含 App Router 页面 chunk、Pages Router 兜底 chunk、polyfills） |
| `total_css_gzip_kb`（全站 CSS） | 12.27 | 20 | `static/css/**/*.css` 全部文件 gzip 求和（当前构建只有 1 个 CSS 文件） |
| `max_chunk_gzip_kb`（最大单 chunk） | 52.40 | 60 | 上述全部 `.js` 中单个文件 gzip 体积的最大值（当前为 `static/chunks/fd9d1056-*.js`，React/Next 运行时） |

阈值规则：**真实基线 × 1.10，向上取整到 10KB**。

- 118.43 × 1.10 = 130.27 → **140**
- 610.52 × 1.10 = 671.57 → **680**
- 12.27 × 1.10 = 13.50 → **20**
- 52.40 × 1.10 = 57.64 → **60**

常量与基线注释放在 `tools/check_bundle_budget.py` 顶部（`DEFAULT_BUDGETS_KB`），
改阈值只改那一处。脚本无第三方依赖，只用 Python 标准库。

### 首屏的取法

首页路由是 `app/(main)/page.tsx`（URL 为 `/`）。脚本在
`app-build-manifest.json` 里按以下顺序找 page 条目：`/(main)/page` → `/page` → `/`；
layout 链用前缀匹配自动解析，因此以后调整路由组目录（例如把首页移出 `(main)`）
仍能正确取到根 layout 与对应分组 layout。若找不到首页条目，脚本会退化为
“rootMainFiles + 根 layout”并在输出里明确打印实际使用的条目，避免假装测了首页。

首屏指标只统计 **JS**；首屏 CSS 当前与全站 CSS 相同（单文件 12.27KB），已由
`total_css_gzip_kb` 覆盖。

## 2. 为什么首屏用“体积代理”

“首屏 1.5s” 是**网络/渲染指标**，取决于用户带宽、RTT、CDN、后端响应、设备 CPU、
甚至字体加载，同一份代码在不同环境能差出数倍。它需要浏览器环境（Lighthouse /
WebPageTest / 真实设备）才能测，不能在纯 Python 的后处理脚本里“算”出来。

体积是首屏耗时里**前端可控且可复现**的那部分：

- 同一份构建产物、同一压缩级别，结果逐字节一致，适合做 CI 门禁；
- 首屏 JS 直接决定下载、解析、执行成本，是 LCP/TBT 的主要可控因子；
- 不需要起服务、装浏览器、连后端，几秒钟跑完，且不会因网络抖动误红。

所以 CI 里用体积做**代理指标**：体积守住，首屏耗时的下限就有保障；真实耗时另行
用 Lighthouse 观测（见第 6 节），不混进本门禁。

## 3. 本地怎么跑

```bash
# 1) 先产出构建产物（体积门禁的输入）
cd apps/web && npm run build

# 2) 回到仓库根目录执行门禁
cd /Users/shanziya/Documents/张阗/ai-eos
python3 tools/check_bundle_budget.py --dir apps/web/.next

# 机器可读输出（供其他脚本消费）
python3 tools/check_bundle_budget.py --dir apps/web/.next --json
```

输出示例：

```text
指标                                      当前      预算      用量
first_load_js_gzip_kb                   118.43    140.00     84.6%
total_js_gzip_kb                        610.52    680.00     89.8%
total_css_gzip_kb                        12.27     20.00     61.3%
max_chunk_gzip_kb                        52.40     60.00     87.3%
```

退出码：

| 退出码 | 含义 |
| ---: | --- |
| 0 | 全部指标在预算内 |
| 1 | 有指标超预算；逐项打印 `current / budget / 超出量` |
| 2 | 构建目录或 manifest 缺失（通常是没先 build），或 manifest 引用的文件不存在 |

`--budget-kb N` 可临时把四项预算统一覆盖为 N KB，**仅用于本地反向验证**
（例如 `--budget-kb 1` 应退出 1）。CI 不传该参数；不要用它来“放宽”门禁。

## 4. CI 接入位置

`.github/workflows/ci.yml` 的 `frontend` job（前端类型检查 + 单元/契约测试）：

1. `npm ci` → `npx tsc --noEmit` → `npm run test`（原有步骤）；
2. **新增** `npm run build`：产出 `.next`，同时兜住 build 期的 lint/类型错误；
3. **新增** `python3 ../../tools/check_bundle_budget.py --dir .next`：体积门禁，
   超预算即 job 红。

不引入新 action、不上传产物、不做部署；需要 `python3`（ubuntu-latest 自带）。
其他 job 未改动。

---

## 5. 阈值调整流程

1. **先测基线**：在目标环境执行 `cd apps/web && npm run build`，再跑本脚本，
   记录四项当前值（不要凭感觉写一个数）。
2. 按 **基线 × 1.10，向上取整到 10KB** 计算新阈值；若确属合理的产品级增长
   （例如新增必需依赖），可在 PR 说明里解释并申请更高系数，但不能降低到基线以下。
3. 修改 `tools/check_bundle_budget.py` 顶部的 `DEFAULT_BUDGETS_KB` 与上方基线注释
   （写清测量日期、Node/Next 版本）。
4. 在 PR 描述里附「调整前基线 → 调整后基线 / 旧阈值 → 新阈值」对比与原因。
5. 阈值只随真实基线走，不允许为了让红变绿而临时调大后不补说明。

## 6. Lighthouse 首屏门禁（已接入）与交互 P95（尚未接入）

### 6.1 Lighthouse（首屏 LCP ≤1.5s）—— 已进入 CI

`apps/web/lighthouserc.json` + `.github/workflows/ci.yml` 的 `lighthouse` job：

- 独立 job：`npm ci` → `npm run build` → `npx @lhci/cli autorun`；
  lhci 自己拉起 `next start -p 3100`，跑 `/login` 3 次取中位数；
- desktop preset（产品主形态是桌面工作台），断言全部为 **error**：

| 指标 | 阈值 |
| --- | ---: |
| Lighthouse 性能分 | ≥ 90 |
| LCP | ≤ 1500 ms |
| TBT | ≤ 200 ms |
| CLS | ≤ 0.1 |

- 本地实测（2026-11-01，M 系列 Mac，Chrome headless）：性能分 100、
  LCP 0.5–0.6s、TBT 0ms、CLS 0.005；
- 本地复跑：
  ```bash
  cd apps/web && npm run build
  npx --yes @lhci/cli@0.15.1 autorun --config=./lighthouserc.json
  ```
  报告落在 `apps/web/.lighthouseci/`（已 gitignore）。
- 若 ubuntu runner 冷启动偶发超标：先看报告里的 LCP 元素与 TTFB，再决定优化
  还是调整阈值；**不要为了变绿把断言改成 warn**。

### 6.2 交互 P95（INP / 本地操作时延）

- “交互 P95”需要真实用户监控（RUM）或端到端脚本在浏览器里打点，依赖浏览器环境、
  真实后端与数据量，当前仓库的 CI 没有这些条件；
- 建议路径：前端接入 `web-vitals` 上报 INP/LCP 到现有事件日志或独立端点，按 P75/P95
  聚合；或在 Playwright 用例里对关键操作（打开工作台、发送消息、切换项目）打
  `performance.now()` 并断言 P95；
- 在具备上述环境前，CI 只用体积代理兜底，文档与 PR 中不要声称已测量首屏耗时或
  交互 P95。
