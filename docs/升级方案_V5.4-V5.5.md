# AI-EOS 升级方案 V5.4–V5.5

> 依据：① GitHub 同类项目调研（Dify / Open WebUI / n8n / Home Assistant /
> Tailscale / 1Panel / Coolify / self-hosted-ai-stack）② V5.3 已落地的局域网共享
> （`/clients/lan` + `/lan-share` 二维码页 + 桌面壳开机自启 + uvicorn 0.0.0.0）。
> 调研为外部摘要，star 数为约数，落地前以官方仓库为准。

## 现状基线（V5.3 已交付，勿重复做）

| 能力 | 位置 |
|---|---|
| 三端一键部署（安装包双击即跑 · 服务器 systemd） | 便携壳 / `服务器一键部署.sh` |
| 开机自启（mac/win 登录项 · linux XDG · systemd） | 桌面壳 IPC + 部署脚本 |
| 局域网共享 + 二维码接入 | `GET /clients/lan`、`/lan-share` 页、壳菜单 |
| 手机 App 接管 | Android「服务器」页填 API 地址 |
| 自动升级 + sha256 + manifest 备份 | V5.2 `/clients/update` + 发布工具 |

## 调研结论：我们缺什么

同类项目里，**部署体验**（Dify 的 compose 一键、1Panel 的应用商店）与
**自动升级**（n8n 的 systemd、self-hosted-ai 的 doctor 自检）我们已经平齐或超过；
真正拉开差距的是三件事——**发现、配对、信任**：

1. Home Assistant 用 mDNS/zeroconf 让设备**自动被发现**（IP 变了也不坏），
   我们现在的二维码写死 `http://IP:port`，换网/换 IP 就失效，手机 App 还要手敲地址。
2. HA 的**扫码 + 6 位码一次性配对**：配完手机就"长住"在系统里，可列可撤；
   我们现在扫码=进登录页，等于没配对，老板的账号密码暴露给手机。
3. Dify/Open WebUI 的**多租户 + 角色账号 + API Key**：手机/集成方可以用
   只读轻账号，而不是共用老板主账号。

## 升级项（按优先级）

### P0 · V5.4「同网自动发现 + 扫码即配对」

**① mDNS 广播（学 Home Assistant）**
- 后端启动时周期广播 `_aieos._tcp`（zeroconf，TXT 带 port/version/hostname），
  服务名 `ai-eos.local`；多实例同网时以 port 区分。
- 桌面壳 / 浏览器 Web：`/lan-share` 页二维码内容升级为 `ai-eos.local:port`
  形式 + 备用明文 IP 链接（iOS Safari 对 .local 解析不稳，双保险）。
- Android App「服务器」页加**自动发现**按钮：扫局域网 `_aieos._tcp`，
  直接列出「你网络里的 AI-EOS」点一下就连上（免手敲 IP）。
- 依赖：后端 `zeroconf`（纯 Python）；App 端 mDNS 扫描需原生模块
  （`react-native-zeroconf` 或 Expo config plugin）——**需先做技术验证**。

**② 配对码 + 设备授权（学 HA 的 6 位码模型）**
- 桌面版「局域网共享」页加 **📱 分享给我手机** 按钮：
  后端生成一次性配对 token（短 TTL 10min + 单次使用 + 绑定设备指纹），
  二维码 URL = `http://IP:port/pair?token=***
- 手机浏览器打开 → 自动登录（免输密码）→ 该手机设备登记进
  `devices` 表（名字/型号/首次访问时间）→ 老板在桌面端可见、可一键撤销
  （撤销=吊销该设备的所有会话 token）。
- 安全边界：token 只能"开登录"，不能直接写数据；写操作仍需密码学验证
  （保留现有全鉴权）。
- 工作量：后端 2 端点 + 1 表 + 前端 2 区块，**1–2 天**。

**③ 诊断命令（学 self-hosted-ai 的 make doctor）**
- `GET /diagnostics`：服务/DB/端口/0.0.0.0 监听/防火墙状态/磁盘/依赖版本
  一键体检，返回 checklist；桌面壳「查看」菜单加「🩺 系统诊断」，
  结果直接在 Web 页渲染，失败项给修复建议（如"防火墙未放行 8001"）。
- 工作量：**1 天**。

### P1 · V5.5「升级与运维增强」

**④ 自动升级：灰度 + 回滚（学 n8n 生产实践）**
- manifest 加 `channel`（stable/canary）：canary 用户先收新版，
  稳定 48h 后 stable 跟进；发布工具 `--channel canary`。
- 「一键回滚」：利用 V5.3 已做的 manifest 备份链（`.bak-时间戳`），
  发布工具加 `--rollback <时间戳>`，客户端下次 check 自动拿回旧版。
- 工作量：**1–2 天**。

**⑤ 系统控制台（学 1Panel 轻量版）**
- Web 新页「系统台」：服务状态（前后端/DB 心跳）、资源占用（CPU/内存/磁盘）、
  日志 tail（最近 100 行）、自启状态、局域网状态（当前 IP/连接设备数）、
  一键重启服务。非技术老板的一站式运维面板。
- 复用 `/diagnostics` 数据，工作量：**2 天**。

**⑥ 角色账号 + API Key（学 Dify / Open WebUI）**
- 老板主账号之外支持 `viewer`（只读）/`operator`（可批任务不可改配置）角色；
  个人 API Key（前缀 `aieos_`）给手机/第三方集成用，Key 可独立吊销。
- 工作量：**2–3 天**（鉴权中间件改造面大，需全链路回归）。

### P2 · 观察项（暂不做）

- **跨公网组网**：手机 4G/异网时推荐 Tailscale（官方免费档够用），
  只写进文档/「边界与安全」卡片，不引入自研中转。
- **iOS 端**：按既定范围排除。
- **Docker 部署形态**：目前"便携壳 + 一键脚本"双轨已覆盖；
  若企业用户强烈要 compose 文件（学 Dify/self-hosted-ai-stack），
  补一个 `docker-compose.yml`（前后端 + Postgres + 可选 Ollama）即可，0.5 天。

| 版本 | 内容 | 预估 |
|---|---|---|
| V5.4 | ②配对码（P0 主体）+ ③诊断 | 3 天内 |
| V5.4+ | ①mDNS（先技术验证，App 端原生模块风险最高） | +2–3 天 |
| V5.5 | ④灰度回滚 + ⑤系统台 + ⑥角色账号 | 1 周 |

## 风险与决策点

1. **mDNS 在 App 端**：Expo 管理版构建（EAS）不支持原生模块需改预构建——
   验证前不排期；验证失败则降级为"App 手动输 IP + Web 页二维码"（现状已可用）。
2. **配对 token 绑定设备指纹**：浏览器指纹弱，用 UA + IP 前 24 位 + 随机 nonce
   三件套近似，不做设备证书（桌面 Web 场景够用）。
3. **角色账号改造面**：现有 60+ 路由全走 `get_current_user`，
   加角色校验需逐路由标注权限位——建议只做"viewer 全只读"一刀切，
   细粒度授权放 V6。
