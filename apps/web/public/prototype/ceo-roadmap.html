03

那根「准绳」：怎么像 Git 一样牵住所有 Agent

核心创新点

不是一句口号，是一个可落库、可注入、可校验的锚对象。四个动作贯穿一场 mission。

STEP 01 · 立锚

开工前先固化

目标、交付物形态、红线、验收标准、术语口径。一经确认即不可变，改就必须升版本。

STEP 02 · 注入

每个子 Agent 都带着

写进 system 段，排在用户消息之前。用户消息只能补细节，覆盖不了红线。

STEP 03 · 自检

交付前先对一遍

子任务完成时比对交付物：格式不对、踩红线、答非所问 → 标「偏离」，打回而不是直接汇总。

STEP 04 · 留痕

一根线查到底

mission 贯穿整棵任务树：谁拆的、派给谁、跑了几次、偏离过几次、最后怎么收的，全可回放。

为什么这一步最值钱：现在多 Agent 出问题，九成不是模型不行，而是「没人记得最初要干什么」。作战室已经证明了 goal + 交付规则一起注入能明显收窄跑偏；我们只是把它从「一场仗」升级成「全公司通用的锚」。
04

并发：2 保底、3 默认、可自定义

按你说的配置

不是把所有子任务一次全扔出去，而是按「供应商真实能力」开闸。

三档开闸规则

保底 2：任何供应商都能扛住，最差情况也不会退化成串行。
默认 3：速度与稳定性的平衡点，开箱即用。
可调 3–10：老板按自己的模型额度往上开，超过就自动排队而不是硬塞。

上限最终取三者最小值：老板设定 ∩ 供应商档位 ∩ 系统 worker 余量

自动降档（不靠人盯）

连续 429 / 超时会自动降回 2 并冷却一段时间；冷却期结束再试探性升回。队列里的任务照常排队，不会因为降档而丢。

每一次降档都写审计日志，面板上能看出「今天为什么只开了 2 个」。

06

需要你拍板的 4 件事

我不会擅自决定

每项都给了我的建议，你点头我就按建议走；你有别的想法直接说。

拍板 1和作战室是什么关系？

作战室已经能做「一个目标 + 一队人 + 汇总」。CEO 是它的放大版，还是另起一套？

建议：内核合并成一套，保留作战室作为「单目标盯盘视图」，避免维护两套并行的实现。

拍板 2CEO 本身算不算一个员工？

是占一个编制、能被换模型/换人，还是一个看不见的系统能力？

建议：算员工、可指派。这样老板能直接换 CEO 的模型，也能让部门负责人当 CEO。

拍板 3并发上限要不要按套餐再收一档？

你说可调 3–10。但真实供应商可能只允许 2 个并发，硬开到 10 就是整批失败。

建议：界面允许 3–10，但服务端按供应商档位封顶，并明示「当前实际可用 3」。

拍板 4定时日报的推送时间和通道？

站内信 / 钉钉等 IM / 手机推送三条通道都已具备，问题只是「什么时候、发到哪」。

建议：默认每天 09:00 站内信 + 手机推送；IM 由你在设置里自己开。
07

做完怎么算成功

可逐条验证

每条都是可以当着你的面演示的，不是「大概能用」。

  • 全链路：一句话 → 拆解预览 → 确认开工 → 3 个并行 → 回收 → 报告归档，中间不用你插手。
  • 准绳有效：故意给一个会跑偏的子任务，系统能标出「偏离」并打回，而不是混进最终报告。
  • 并发可控：设 2 就最多 2 个在跑；模拟 429 后自动降档且不丢任务；恢复后能升回去。
  • 失败可追：某个子 Agent 挂了，报告里必须点名是谁、卡在哪一步，不能只写「部分失败」。
  • 不回归：现有后端测试全绿；作战室、一句话指挥台老路径行为不变。
  • 不花钱不乱跑：模型调用失败有明确降级；高风险动作仍然走人工审批门，CEO 不能替老板按同意。
